# 설계 제안: 역할 기반 API 권한과 판정 일관성

- 상태: 검토 중
- 작성일: 2026-11-03
- 담당: 미정
- 관련 문서/ADR: [2단계 인증과 권한](../stages/backend/stage-02-authentication.md), [아이디·비밀번호 로그인과 JWT](../decisions/ADR-009-username-password-jwt.md)

## 문서 관리 원칙

권한 모듈의 정책·구조 설계와 보완 논의는 현재 이 제안 문서에서 관리하며 추후 별도 설계 문서로 이관합니다. 2026-11-04 사용자 지시에 따라 스키마 정의는 [인증·권한 테이블 정의서](../db-schema/tables/auth/README.md)에서 먼저 관리하고 이 문서에서는 링크로 연결합니다. 그 밖의 관련 문서는 이 제안서를 링크하고 현재 구현 상태와 진행 상황을 기록하며 상세 설계를 중복 작성하지 않습니다.

## 문제와 목표

현재 로그인과 JWT 인증은 구현되어 있지만, 사용자별 작업 허용 여부를 결정하는 권한 모델은 아직 없습니다. 모든 API의 접근 정책을 식별 가능하게 하고, 사용자와 역할에 권한을 부여하며, 민감한 권한 변경이 오래된 판정으로 사용되지 않도록 하는 설계가 필요합니다.

목표는 다음과 같습니다.

- 모든 API 엔드포인트가 공개 여부와 권한 식별자를 명시합니다.
- 사용자·역할·권한을 분리해 최소 권한 원칙에 따라 구성합니다.
- 권한 캐시를 사용할 API와 매 요청 DB 조회가 필요한 API의 정책을 구분합니다.
- 권한 변경과 보호 작업이 경합할 때 민감한 변경이 권한 회수보다 뒤늦게 커밋되지 않도록 합니다.

## 범위와 제외 범위

포함 범위:

- Nexus Repository의 RBAC 개념을 참고한 사용자·역할·권한 모델
- 전 API 권한 식별자 및 계층 이름 규칙
- JWT와 서버 인가 정보의 책임 경계
- TTL 캐시와 매 요청 조회의 혼합 정책
- 민감한 작업의 권한 확인·DB 변경 트랜잭션 경계

초기 범위에서 제외:

- 사용자 그룹 및 외부 LDAP/SSO 그룹 동기화
- 리소스 경로 선택자와 임의 정책 언어
- 거부 권한(deny)과 역할 간 상속
- 구현, 보안 규정 준수 판정

## 제안 설계

### 1. RBAC 구성

Nexus의 핵심 구조처럼 권한을 역할에 묶고 역할을 사용자에게 부여합니다. 한 사용자에게 여러 역할을 부여할 수 있습니다. 초기에는 그룹을 도입하지 않고 사용자에게 직접 역할을 할당합니다. 팀별 일괄 관리나 외부 디렉터리 연동이 필요해지면 사용자 그룹을 추가합니다. Nexus는 privilege를 role에 묶고 role을 user 또는 group에 할당하는 모델을 제공합니다. [Nexus 접근 제어](https://help.sonatype.com/en/access-control.html)

```mermaid
flowchart LR
    User[사용자] --> UserRole[사용자 역할 연결]
    UserRole --> Role[역할]
    Role --> RolePermission[역할 권한 연결]
    RolePermission --> Permission[권한]
```

컬럼·PK/FK・유일 제약・인덱스・삭제 규칙은 [인증·권한 테이블 정의서](../db-schema/tables/auth/README.md)에서 관리합니다. 기존 `auth_user`와 신규 권한 테이블 4개의 관계를 정의했으며, 신규 테이블은 설계 초안으로 DB에 적용하지 않았습니다. 초기에는 매 요청 DB 조회를 사용하고 캐시 정책 컬럼은 8단계에서 필요성을 검토합니다.

그룹이 필요한 시점에 `auth_group`, `auth_group_user`, `auth_group_role`을 추가할 수 있습니다. 처음부터 사용자와 그룹을 일반 주체 테이블로 통합하는 방식은 초기 구현을 복잡하게 하므로 제안하지 않습니다.

### 2. 모든 API의 권한 식별자

각 API 엔드포인트는 공개 또는 비공개 정책을 명시합니다. 세부 권한이 필요한 비공개 API만 권한 코드를 지정하고, 공개·인증 전용 API에는 DB 권한 코드를 요구하지 않습니다.

#### 접근 정책 단순화 — 2026-11-06 확정

사용자 결정에 따라 API 접근은 공개 또는 비공개(권한 필요)로 구분합니다. 비공개 API의 권한 요구 수준은 인증만 필요하거나 세부 권한 필요 중 하나입니다. 기존 세 가지 병렬 접근 유형 제안 대신 이 구조를 사용합니다.

| 공개 여부 | 권한 요구 수준 | 판정 |
|---|---|---|
| 공개 | 해당 없음 | 인증 불필요 |
| 비공개 | 인증만 필요 | 인증된 활성 계정이면 역할·세부 권한 없이 허용 |
| 비공개 | 세부 권한 필요 | 인증된 활성 계정이며 지정된 세부 권한이 있어야 허용 |

- 비공개 API는 권한 조회 전에 인증 여부를 확인합니다. 인증 정보가 없거나 유효하지 않으면 권한 부족으로 분류하지 않고 401로 처리합니다.
- 인증 후 세부 권한이 없으면 403으로 처리합니다. 계정 없음·비활성은 기존 계약대로 401이며, 조회 장애는 서버 오류로 처리합니다.
- 「인증만 필요」는 모든 권한을 가진 역할이나 와일드카드 권한이 아닙니다. 별도 DB 권한 행이나 역할 할당 없이 해당 API에 접근할 수 있다는 의미입니다.
- API 정책 선언 누락은 인증 여부만으로 허용하지 않습니다. 기동 시 전수 검사는 하지 않으며 선언 누락은 개발자 오류로 다룹니다. 요청 시 기본 거부 원칙은 유지합니다.
- 구현 시 공개 선언과 비공개 권한 요구 선언을 명시적으로 구분하고, 공개와 세부 권한을 동시에 선언하지 않도록 작성합니다. 선언 오류 자동 검출을 위한 별도 기능은 추가하지 않습니다. 구체적인 어노테이션 이름·속성은 5단계 코드 작성 시 이 규칙에 맞춥니다.

식별자 형식은 `도메인:리소스:동작`을 제안합니다. 계층은 분류와 검색을 위한 네임스페이스이며, 부모 권한이 자식 권한을 자동 허용하지 않습니다.

현재 API와 향후 API 예시의 목록 및 접근 정책은 아래 1단계 상세안에서 구분해 관리합니다. 공개·인증 전용 API의 식별자는 문서상 분류이며 실제 어노테이션에서 코드를 요구하거나 역할에 부여하지 않습니다.

역할에는 필요한 권한만 명시적으로 연결합니다. 예를 들어 데이터셋 관리 역할에 읽기·생성·수정은 주되 삭제는 주지 않을 수 있습니다. 권한이 명시적으로 연결되지 않은 API는 거부합니다.

Spring Security에서는 컨트롤러 또는 중앙 API 보안 메타데이터에 권한을 연결하고, `@PreAuthorize` 등의 공통 인가 지점에서 검사합니다. 권한 식별자는 일관되게 관리하되 선언 누락·불일치 자동 검출을 위한 기동 검사기나 전용 프레임워크는 추가하지 않습니다.

### 3. JWT와 권한 정보

JWT는 사용자 식별 및 인증에 사용하고, 권한 목록을 인가의 최종 근거로 싣지 않습니다. 토큰에 권한을 넣으면 역할 회수 후에도 토큰이 만료될 때까지 이전 권한이 유효할 수 있습니다.

사용자 인터페이스가 메뉴 표시 등을 위해 권한 요약을 필요로 하면 응답 API로 제공할 수 있지만, UI가 표시한 권한을 서버가 신뢰해서는 안 됩니다. 서버는 모든 API 요청에서 인가 여부를 판정합니다. OWASP도 권한 검사를 각 요청에 적용하고 기본 거부 원칙을 권고합니다. [OWASP 권한 부여 지침](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

### 4. TTL 캐시와 매 요청 DB 조회 혼합

요청에서 필요한 권한은 조회 정책에 따라 판정합니다.

| 정책 | 적용 후보 | 권한 회수 반영 |
|---|---|---|
| 매 요청 DB 조회 | `auth:user:manage`, `auth:role:manage`, 삭제·공유 등 영향이 큰 권한 | 다음 요청부터 확인 가능 |
| 짧은 TTL 캐시 | 일반 조회 등 권한 회수 지연을 제한적으로 허용하는 권한 | 최대 TTL만큼 지연 가능 |

캐시 TTL 동안 회수된 권한이 잠시 허용될 수 있음을 정책으로 명시합니다. TTL 캐시를 강한 회수 보장으로 취급하지 않습니다. 초기 기본값은 매 요청 조회로 두고, 위험과 부하를 검토한 뒤 지연을 허용할 권한에만 TTL을 도입하는 점진적 방식을 제안합니다. 구체적인 권한별 분류와 TTL은 미결정입니다.

### 5. 요청 처리 중 권한 변경 및 강한 통제

HTTP 응답 직전의 추가 권한 조회는 회수 사실을 감지할 수 있지만 이미 커밋된 변경이나 외부 부작용을 되돌리지 못합니다. 따라서 민감한 DB 변경은 권한 확인과 데이터 변경을 하나의 트랜잭션 경계에 둡니다.

- 보호 작업은 트랜잭션 안에서 권한을 확인하고 도메인 변경을 수행합니다.
- 권한 회수와 보호 작업의 동시 실행 순서를 정의합니다. 필요한 경우 권한 행 잠금, 권한 버전 조건, 조건부 DML 등 DB에서 확인과 변경을 조율하는 방법을 선택합니다.
- 권한 회수와 작업이 경합하면 먼저 DB에서 확정된 순서에 따라 하나가 완료되고, 오래된 권한을 사용한 작업은 거부되도록 합니다.
- 작업이 외부 서비스 호출이나 파일 저장 등 DB 트랜잭션 밖 부작용을 포함하면, 호출 전 권한 재확인만으로 원자성을 보장할 수 없습니다. outbox, 취소 또는 보상 동작은 해당 기능 설계에서 다룹니다.

권한을 트랜잭션과 어떻게 잠글지, 허용 가능한 동시성 규칙은 사용하는 DB와 작업 특성에 맞춰 구현 전에 결정해야 합니다. 검증과 사용 사이의 경쟁 조건(TOCTOU)을 줄이려면 중요한 동작의 최종 실행 게이트가 실제 실행에 결속되어야 합니다. [OWASP 트랜잭션 권한 부여 지침](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html)

## 대안과 장단점

| 대안 | 장점 | 단점 | 평가 |
|---|---|---|---|
| 모든 권한을 매 요청 DB 조회 | 회수 반영이 단순하고 빠름 | 권한 조회 비용 증가 | 초기 기본값으로 권장 |
| 모든 권한을 TTL 캐시 | DB 부하와 지연 감소 | TTL 동안 오래된 권한이 허용될 수 있음 | 단독 적용 비권장 |
| JWT에 권한만 포함 | 서버 조회 최소화 | 토큰 만료 전 권한 회수가 어려움 | 인가의 최종 근거로 사용하지 않음 |
| 권한별 DB 조회/TTL 혼합 | 위험도와 비용을 절충 | 권한별 지연 정책과 캐시 관리 필요 | 점진적으로 도입 제안 |
| 사용자 그룹을 처음부터 지원 | 팀 단위 할당을 바로 지원 | 모델·API·운영 복잡도 증가 | 실제 수요 시 도입 |

## 보안·운영

- 권한은 기본 거부하고 필요한 역할에 최소 권한을 명시적으로 연결합니다.
- `ADMIN` 역할은 모든 권한을 포함하는 시스템 역할로 다룰 수 있으나, 생성·부여·회수 절차와 최초 관리자 bootstrap은 별도 설계가 필요합니다.
- 로컬 개발용 관리자 계정은 로컬 전용 seed로 제공할 수 있습니다. 테스트 seed와 운영 계정은 분리해야 하며, 비밀번호는 해시로만 저장합니다.
- 권한 변경 감사 기록, 관리자 자기 권한 부여 방지, 마지막 관리자 보호, 계정 비활성화 및 토큰 정책은 별도 보안 요구사항으로 구체화합니다.
- 권한 스키마는 각 테이블 정의서에 기록합니다.
- 보안 규정 준수 여부는 기존 TODO 추적 원칙을 따르며 이 제안만으로 준수를 선언하지 않습니다.

## 구현 및 검증 계획

### 구현 범위 조정 — 2026-11-06

- 사용자 지시에 따라 5단계 시작 전 상태로 유지합니다. 5단계 소스코드는 아직 추가되지 않아 제거할 구현은 없으며, 1~4단계 결과는 보존합니다.
- 기동 시 어노테이션 누락·충돌 등을 전수 검사하는 계획은 취소합니다. 선언 오류는 개발자 책임으로 다루고 전용 검사 코드는 추가하지 않습니다.
- 실제 요청의 인증·권한 판정은 유지하고, 가능한 한 적은 코드로 기능을 구현합니다. 순수 기능 외 개발은 반드시 사용자 사전 승인을 받습니다. 당시 5단계는 미착수로 유지했으며, 이후 사용자 지시에 따라 아래 최소 기능 범위로 구현을 재개했습니다.

### 전체 진행 현황 — 2026-11-06

초기 우선순위 계획과 이후 합의한 스키마 선행 순서, API·서비스·비동기 TODO를 아래 10개 작업 단계로 통합해 진행 현황을 표시합니다. 아래 번호가 현재 작업 순서의 기준이며, 뒤의 기존 단계 기록은 당시 경과와 세부 요구사항을 보존합니다. 초기 역할·접근 정책의 미결정 사항은 관련 단계에서 확정해야 합니다.

| 단계 | 작업 | 상태 | 완료 범위 또는 남은 작업 |
|---|---|---|---|
| 1 | 스키마·테이블 정의서 | 완료 | 기존 auth_user 유지, 신규 권한 테이블 4개 정의 |
| 2 | 도메인·DAO·서비스 계약 | 완료 | auth 내부 배치, 유효 권한 전용 DAO, requirePermission 계약 |
| 3 | 권한 판정 로직·단위 검증 | 완료 | 활성 계정·명시 권한 검사, 거부·장애 처리 |

| 6 | 서비스 경계·비동기 인가 | 보류 | 서비스 직접 호출 또는 비동기 작업에서 별도 인가가 필요해지면 재개 |

1~5단계는 완료했고 당시 전체 테스트 30개가 통과했습니다. 2026-11-07에 6단계를 보류했습니다. 업무 서비스가 추가되고 서비스 직접 호출의 권한 검사나 비동기 작업의 실행 주체 전달이 필요해지면 해당 호출 경로를 기준으로 재개합니다. 마지막 10단계는 필요성 측정에 따른 선택 사항입니다.

### 스키마 정의 선행 작업 — 2026-11-04

- 사용자 지시에 따라 모듈 계약·판정 코드·DB 적용에 앞서 스키마 정의서를 작성했습니다. 이후에는 스키마를 바탕으로 도메인·DAO·인가 서비스 계약을 정하고 판정 구조를 검증한 뒤 실제 DB와 데이터를 연결합니다.
- 결과: [테이블 정의서 목록과 관계](../db-schema/tables/auth/README.md). 신규 4개 테이블의 컬럼·키·인덱스·삭제 규칙과 기존 사용자 키 호환 방식을 정의했습니다.
- 상태: 정의서 초안 작성. DAO·초기 데이터는 미구현이며 DB 검증은 수행하지 않았습니다. 1단계의 역할·접근 정책 질의도 아직 미확정입니다.
- 2단계의 불변 사용자 ID 도입 여부가 확정되면 사용자 및 연결 키를 함께 갱신한 뒤 실제 DB 적용에 들어갑니다.

### 스키마 정의 후 2단계: 모듈 계약 정의 — 완료

2026-11-04 사용자와 정리한 진행 순서는 스키마 정의 → 모듈 계약 정의 → 판정 구조 구현·검증 → DB 적용입니다. 이 절의 2단계는 아래 기존 우선순위 계획의 「2단계: 사용자 식별과 계정 상태 검증 강화」와 구분합니다. 기존 우선순위 항목은 구현 시 확인할 보안 요구사항으로 유지합니다.

- 확정: 사용자 계정 테이블명은 기존 `auth_user`를 유지합니다. 이는 테이블명 확정이며 불변 사용자 ID 도입 여부까지 결정한 것은 아닙니다.
- 이번 작업: 도메인 모델, DAO 조회 계약, 다른 모듈이 호출할 인가 서비스 경계를 정의합니다. 테이블 생성·MyBatis SQL·기본 데이터는 이후 DB 적용 단계에서 연결합니다.
- 기존 계약: `AuthUser(username, passwordHash, enabled)`, `AuthUserDao.findByUsername`은 유지합니다. 인가 응답에 비밀번호 해시를 노출하지 않습니다.

#### 선택 1: 모듈 배치 — 확정

사용자 선택: 기존 `auth` 내부에 구성합니다. 아래 표의 첫 번째 안을 채택했습니다.

| 선택지 | 내용 | 영향 |
|---|---|---|
| 기존 `auth` 내부 구성 — 권장 | `domain`, `dao`, `service` 및 기존 `config` 경계 활용 | 기존 모듈 책임·저장소 지침과 일치 |
| `authorization` 모듈 분리 | 인증과 인가를 별도 기능 모듈로 분리 | 모듈 경계와 기존 지침 변경을 함께 검토해야 함 |

#### 선택 2: 권한 조회 DAO — 확정

사용자 선택: 사용자 유효 권한 조회 전용 DAO를 사용합니다. 아래 표의 첫 번째 안을 채택했습니다.

| 선택지 | 내용 | 영향 |
|---|---|---|
| 유효 권한 조회 전용 DAO — 권장 | username으로 역할에 연결된 권한 코드의 중복 없는 집합 조회 | 서비스가 테이블 조인 구조를 몰라도 되고 MyBatis에서 한 번에 조회 가능 |
| 테이블별 DAO 조합 | 사용자 역할과 역할별 권한을 각각 조회해 서비스에서 합침 | 개별 저장 계약은 명확하나 조회 횟수·조합 로직 관리가 필요 |

#### 선택과 무관하게 지킬 계약

- 역할·권한 코드와 연결 모델은 테이블 정의서의 이름·형식·키에 맞춥니다. 스키마에 없는 사용자 ID나 캐시 필드를 임의로 추가하지 않습니다.
- 인가 서비스의 입력은 서버가 검증한 사용자 식별자와 필요한 권한입니다. 클라이언트가 전달한 사용자명·권한 목록을 인증 근거로 사용하지 않습니다.
- 역할 없는 활성 사용자의 유효 권한은 빈 집합입니다. 조회 장애를 빈 집합이나 허용으로 바꾸지 않습니다.
- 공개·인증 전용 API의 추적용 식별자는 부여 가능 권한과 구분합니다. 권한 판정 성공만으로 리소스 소유권·공유 범위를 통과한 것으로 간주하지 않습니다.
- 테스트용 DAO 구현은 테스트 소스에 한정합니다. 실제 DAO가 없는 상태에서 운영용 허용 구현을 자동 등록하지 않습니다.
- 세 선택을 반영해 아래 도메인 모델·DAO·인가 서비스 인터페이스를 작성했습니다. 계약 정의 단계의 완료이며 실제 인가 동작은 후속 단계에서 구현합니다.

#### 작성한 도메인·DAO 계약

| 패키지 | 타입 | 책임 |
|---|---|---|
| `auth.domain` | `AuthRole` | 역할 코드·표시 이름·설명·시스템 역할 여부 |
| `auth.domain` | `AuthPermission` | 권한 코드·표시 이름·설명 |
| `auth.domain` | `AuthUserRole` | 사용자명·역할 코드 연결 |
| `auth.domain` | `AuthRolePermission` | 역할 코드·권한 코드 연결 |
| `auth.dao` | `EffectivePermissionDao` | 사용자 유효 권한 코드 집합 조회 |
| `auth.service` | `AuthorizationService` | 필요한 권한이 없으면 예외로 실행 중단, 후속 판정 단계에서 구체 클래스로 전환 |

- 조회 계약: `Set<String> findEffectivePermissionCodesByUsername(String username)`.
- 여러 역할의 권한은 중복 없이 반환하고 미부여는 빈 집합으로 반환합니다. 조회 장애는 예외로 전파합니다. DB 구현은 없으며 Spring 빈도 등록하지 않았습니다.
- 사용자 식별자는 기존 `username`을 사용합니다. 계정 존재·활성 상태 확인은 인가 서비스 책임이며 DAO 권한 집합만으로 인증을 인정하지 않습니다.
- record는 스키마와 대응하는 데이터 모델입니다. 코드 형식·필수값 검증 및 인가 판정 로직을 구현한 것으로 간주하지 않습니다.
- 검증: 별도 JDK 21의 `javac --release 21`로 신규 모델 4개와 DAO·인가 서비스 인터페이스의 컴파일을 확인했습니다. `git diff --check`도 통과했습니다. 전체 Maven 테스트와 DB 검증은 실행하지 않았습니다.

#### 선택 3: 인가 서비스 호출 방식 — 확정

사용자 선택: `requirePermission` 방식을 사용합니다. 아래 표의 첫 번째 안을 채택했습니다.

| 선택지 | 내용 | 영향 |
|---|---|---|
| `requirePermission` — 권장 | 권한이 없으면 예외로 실행 중단 | 호출부의 boolean 검사 누락을 줄임 |
| `hasPermission` | 허용 여부를 boolean으로 반환 | 호출부가 반환값을 확인하고 거부 처리를 수행해야 함 |

인가 서비스 계약은 `void requirePermission(String authenticatedUsername, String permissionCode)`입니다. 사용자명은 서버가 검증한 인증 정보에서, 권한 코드는 서버의 부여 가능 권한 카탈로그에서 가져옵니다.

| 결과 | 서비스 계약 | 향후 HTTP 연결 |
|---|---|---|
| 활성 사용자에게 권한 있음 | 정상 반환 | 보호 작업 진행, 리소스 접근 범위는 별도 검사 |
| 계정 없음·비활성 | `BadCredentialsException` | 401로 연결 |
| 활성 사용자에게 권한 없음 | `AccessDeniedException` | 403으로 연결 |
| 입력 누락·권한 코드 형식 오류 | `IllegalArgumentException` | 서버 호출 계약 위반으로 취급, 권한 부여로 해석하지 않음 |
| DAO 조회 장애 | 원래 조회 예외 전파 | 서버 오류로 처리하고 보호 작업 중단 |

예외는 기존 Spring Security 타입을 사용하며 계정 없음·비활성은 동일하게 처리합니다. 인터페이스의 예외 계약을 정의한 것으로, 실제 검증과 HTTP 예외 매핑을 구현한 것은 아닙니다. 서비스 구현은 활성 계정 확인과 명시적 권한 조회를 수행하고, 호출부는 정상 반환 후에만 보호 작업을 실행해야 합니다.

2단계 완료 시점의 범위는 모델 4개, 전용 DAO 인터페이스, 인가 서비스 인터페이스 및 입출력·실패 계약입니다. 서비스는 아래 3단계에서 구체 클래스로 전환했습니다. 2단계 당시에는 API 인가 경로에 연결하지 않았으며 현재 연결 상태는 아래 5단계 기록을 참고합니다.

### 스키마 정의 후 3단계: 판정 구조 구현·검증 — 완료

- 구성: `AuthorizationService`를 인터페이스에서 생성자 주입 방식의 구체 클래스로 전환했습니다. `AuthUserDao`, `EffectivePermissionDao`에 의존하며 별도 서비스 구현 인터페이스를 유지하지 않습니다.
- 판정 순서: 입력 형식·길이 확인 → 사용자 존재·활성 상태 확인 → 유효 권한 조회 → 필요한 권한의 정확한 일치 검사입니다. username은 기존 스키마와 동일하게 최대 100자, 권한 코드는 최대 150자와 세 구간 형식을 확인합니다. 대소문자 변경이나 공백 제거로 입력을 보정하지 않습니다.
- 미부여는 `AccessDeniedException`, 계정 없음·비활성은 동일한 `BadCredentialsException`으로 거부합니다. 조회 예외는 그대로 전파하고 DAO가 null 집합을 반환하면 계약 위반으로 실패합니다.
- 판정 결과를 캐시하지 않아 다음 호출에서 변경된 계정 상태와 권한을 다시 확인합니다. 이는 호출 간 변경 반영이며 동시 회수와 보호 작업의 커밋 순서까지 보장하지 않습니다.
- 테스트 대역은 테스트 소스의 DAO 람다로만 구성합니다. 실제 권한 DAO가 없으므로 서비스는 아직 Spring 빈으로 등록하지 않고 JWT 필터·컨트롤러에도 연결하지 않습니다.
- 입력 형식 검증은 구현했지만 전역 권한 카탈로그와 공개 API 식별자 분류는 아직 연결하지 않았습니다. 호출부는 서버에서 정한 부여 가능 권한 코드를 사용해야 하며, DB 적용·API 인가 연결 전에 카탈로그와 저장 권한의 정합성 검증을 추가해야 합니다.
- 후속 작업: 실제 MyBatis DAO·초기 데이터, Spring 빈 및 HTTP 401/403 처리 연결, API 정책 선언, 리소스 범위 검사와 강한 회수 통제입니다.
- 검증: 2026-11-04 JDK 21·Maven 3.9.11에서 `mvn test` 성공 — 전체 11개, 실패·오류·건너뜀 0개. 신규 `AuthorizationServiceTest` 7개는 명시 권한 허용·미부여 거부, 역할명·와일드카드 우회 거부, 계정 없음·비활성, 잘못된 입력, 조회 장애, null 반환 계약 위반, 다음 호출의 회수·비활성 반영을 검증합니다. 기존 기반 통합 테스트 4개도 통과했습니다. 신규 RBAC 테이블에 대한 DB 검증이나 HTTP 인가 테스트는 아직 수행하지 않았습니다.

### 스키마 정의 후 4단계: DB 적용과 실제 DAO 연결 — 완료

- 신규 권한 테이블 4개와 복합 PK·FK·역방향 조회 인덱스를 사용합니다. 역할·권한·계정 할당 데이터는 자동 생성하지 않습니다.
- `MyBatisEffectivePermissionDao`는 `@Qualifier("appSqlSessionTemplate")`로 app 데이터소스를 명시합니다. MyBatis XML의 매개변수 바인딩과 `SELECT DISTINCT`로 사용자의 여러 역할에 연결된 권한 합집합을 조회합니다.
- 계정 상태와 권한 조회는 MyBatis 로컬 캐시를 비우고 2차 캐시를 사용하지 않도록 설정했습니다. 같은 세션에서 이전 조회 결과를 재사용하지 않으며, DB 격리 수준에 따른 가시성이나 회수 경합의 원자성까지 보장하는 것은 아닙니다.
- `AuthorizationService`를 Spring 빈으로 등록하고 실제 사용자·권한 DAO를 주입합니다. API 어노테이션·인터셉터·Method Security에는 아직 연결하지 않았습니다.
- 외부 DB에 직접 적용하거나 초기 관리자 데이터를 생성하지 않았습니다.
- `AuthorizationDatabaseTest`는 H2에서 신규 생성, 권한 합집합과 사용자 격리, 회수·비활성 반영, 중복·FK·부모 삭제·키 변경 제약을 검증합니다. fixture는 테스트 트랜잭션에서만 생성하고 롤백합니다.
- 초기 `ADMIN`·`MEMBER` 및 권한 부여 정책은 기존 질의가 미확정이므로 이번 범위에 포함하지 않습니다. 불변 사용자 ID 전환 역시 보류하고 기존 `auth_user.username` 참조를 유지합니다.
- 통합 검증에서 기존 `AuthUser.xml`의 생성자 매핑 오류를 발견해 `enabled`의 MyBatis 타입을 `boolean`(래퍼)에서 `_boolean`(원시 타입)으로 수정했습니다. 계정 조회와 실제 인가 서비스 연결 테스트로 확인했습니다.

### 5단계: 최소 API 인가 구현 — 완료 (2026-11-06)

- `@PublicApi`는 공개, 값 없는 `@RequirePermission`은 인증된 활성 계정, 값이 있는 `@RequirePermission("dataset:item:read")`은 해당 권한까지 요구합니다. 컨트롤러 메서드에 선언하고 클래스 수준의 포괄 허용은 사용하지 않습니다.
- 전역 `ApiAuthorizationInterceptor`가 JWT 인증 정보에서 사용자명을 얻어 `requireActiveAccount` 또는 `requirePermission`을 호출합니다. 미인증은 권한 조회 전에 401, 계정 없음·비활성은 401, 세부 권한 부족은 403, DB 조회 장애는 500입니다. 거부된 요청에서는 컨트롤러를 실행하지 않습니다.
- Spring Security의 URL별 허용 목록은 제거하고 MVC 인가는 인터셉터 한 곳에서 판정합니다. JWT 검증과 기존 Spring CORS 처리는 필터 체인에 유지합니다. 메서드 선언 없는 MVC 핸들러·정적 리소스 핸들러는 기본 거부하고, 비-MVC 서블릿은 현재 제공하지 않습니다. 향후 별도 서블릿을 추가하면 별도 보안 경계를 검토해야 합니다.
- 직접 `/error`는 기본 거부하고, 표준 오류 상태 속성이 있는 `/error`의 내부 ERROR 디스패치만 원래 오류를 렌더링합니다. 정상 CORS preflight는 인터셉터 전에 처리하며 일반 OPTIONS를 포괄 허용하지 않습니다. HEAD는 GET 정책을 따릅니다.
- JWT 필터는 MVC ASYNC 재디스패치에서도 토큰을 검증하고, 인터셉터는 계정·권한을 다시 확인합니다. 이는 6단계의 작업 내부 비동기 실행기·큐 인증 전달과 구분합니다.
- 로그인·헬스체크에 공개 선언을 적용했습니다. 실제 보호 업무 API가 아직 없으므로 인증·세부 권한 경로는 테스트 전용 컨트롤러로 검증했습니다.
- 기동 검사기·전수 스캔·전용 선언 검증 프레임워크·권한 카탈로그 프레임워크·권한 자동 등록은 추가하지 않았습니다. 선언 누락·충돌은 요청 시 기본 거부하고 코드 작성 책임으로 다룹니다.
- 검증: `mvn test` 전체 30개 성공(실패·오류·건너뜀 0). 신규 요청 테스트 9개는 공개·인증 전용·세부 권한, 만료·잘못된 토큰, 비활성·삭제 계정, 권한 회수, 선언 없는 요청, CORS, HEAD·ASYNC·ERROR, DB 장애와 컨트롤러 미실행을 확인했습니다. MockMvc 기반이며 실제 네트워크 브라우저 시험과는 구분합니다.

아래 항목은 기존 우선순위 계획이며, 현재 구현 진행은 위 스키마 정의 후 단계별 기록을 기준으로 확인합니다. API 정책·관리자 데이터 등 미결정 항목은 그대로 남아 있습니다. 상세 정책 설계는 이 제안 문서에서 관리하고 추후 별도 설계 문서로 이관합니다.

### 1단계: 접근 정책과 권한 식별자 확정 — 최우선

- 완료 조건: 모든 현재 API에 정책이 있으며, 요청에 필요한 접근 정책과 최소한의 공통 판정 방식이 정해져 있습니다. 선언 누락 등의 개발자 오류를 전수 검사하는 기능은 제외합니다.

#### 현재 API 목록과 접근 정책 초안

| HTTP 메서드 | 경로 | 식별자 | 현재 구현의 접근 정책 | 제안 정책 |
|---|---|---|---|---|
| POST | `/api/auth/token` | `auth:token:issue` | 비인증 접근 허용, 요청한 계정 자격 증명 검증 | 공개 유지 |

#### 초기 역할과 부여 권한 초안 — 질의 중

- 권장안: `ADMIN`, `MEMBER` 두 역할로 시작하고 복수 역할의 명시적 권한 합집합을 사용합니다. 역할 이름만으로 우회 허용하지 않습니다.
- 현재 두 API는 공개이므로 역할에 부여할 필수 권한이 없습니다. 내 정보 조회가 인증 전용으로 정해지면 역할 없는 활성 사용자도 본인 정보를 조회할 수 있습니다.
- 향후 `MEMBER` 후보 권한은 `image:generation:create`, `dataset:item:read`이며 데이터셋 읽기는 소유권·공유 범위로 제한합니다. 삭제 권한은 기본 부여하지 않는 안을 제안합니다.

- 미구현 기능의 후보 권한을 현재 DB에 미리 부여하지 않습니다. 새 권한을 도입할 때 역할별 부여 여부를 명시적으로 검토하는 안을 권장합니다.

#### API 정책 선언과 최소 구현 원칙

- 정책 선언은 컨트롤러 메서드의 전용 어노테이션 한 곳에 둡니다. 공개 여부와 비공개 API의 권한 요구 수준(인증만 필요·세부 권한 필요)을 명시합니다. 클래스 수준의 포괄 허용은 사용하지 않는 안을 제안합니다.
- 최소 구현에서는 `@RequirePermission`에 세부 권한 코드를 명시하고 DB에 연결된 권한과 정확히 비교합니다. 별도 권한 카탈로그 프레임워크나 자동 등록은 추가하지 않습니다.
- API별 메서드·경로 목록을 보안 설정에 다시 수기로 복제하지 않고, Spring MVC의 실제 `RequestMappingHandlerMapping`과 어노테이션을 연결해 공통 인가에 사용합니다. 메타데이터 누락은 기본 거부합니다.
- 식별자 형식은 소문자 영문으로 시작하고 영문·숫자·하이픈을 허용하는 세 구간으로 제한합니다. 검증식 후보는 `^[a-z][a-z0-9-]*:[a-z][a-z0-9-]*:[a-z][a-z0-9-]*$`이며 와일드카드·상위 권한 자동 허용은 지원하지 않습니다.
- RBAC 테이블이 추가되는 3단계 이후에는 정책에서 참조하는 부여 가능 권한과 DB 기본 권한의 일치를 검증합니다. 4단계에서는 실제 요청을 사용해 HTTP 메서드 우회, 미등록 경로, ERROR 디스패치, HEAD·CORS preflight 처리와 기본 거부를 검증합니다.
- 어노테이션·공통 API 인가는 아래 5단계에서 구현합니다. 개발자 선언 오류를 위한 별도 스캔·기동 검증·전용 테스트 프레임워크는 구현하지 않습니다.

#### 사용자 질의

1. 초기 역할을 `ADMIN`·`MEMBER`로 시작하고 관리자도 명시적으로 부여된 권한만 사용하도록 할 것인가? 대안은 신규 권한까지 자동 허용하는 관리자 역할이다.

- 선행: 4단계. 민감한 변경 API를 제공하기 전에 완료합니다.
- 작업: 보호 작업, 사용자 역할 회수, 역할 권한 변경이 공통으로 따를 잠금 또는 버전 규칙과 잠금 순서를 정합니다. 같은 트랜잭션에 포함하는 것만으로 경합이 해결된다고 간주하지 않습니다.
- 작업: 회수가 먼저 확정되면 작업을 거부하고, 작업이 먼저 실행 권한을 확보하면 작업 커밋 이후 회수가 완료되는 등 허용 순서를 명시합니다. 외부 호출·파일 저장은 기능별 outbox 또는 보상 정책을 별도로 정합니다.
- 완료 조건: 양쪽 실행 순서의 경합, 역할 변경으로 여러 사용자가 영향을 받는 경우, 실패 시 롤백과 잠금 충돌 처리를 대상 DB에서 검증합니다. H2 검증만으로 운영 DB의 동시성 보장을 선언하지 않습니다.

### 6단계: 관리자 운영과 권한 변경 감사 — 높음

- 선행: 5단계. 관리자 변경 API를 제공하기 전에 완료합니다.
- 작업: 최초 운영 관리자 생성 절차, 관리자 권한 위임 범위, 자기 권한 상승 방지, 마지막 관리자 제거·비활성화 방지 규칙을 구현합니다. 새 권한 추가 시 `ADMIN`에 자동 부여할지도 정합니다.
- 작업: 권한 변경의 수행자·대상·변경 전후 값·시각·결과를 기록하고 성공한 변경과 감사 기록의 일관성을 보장합니다. 동시 관리자 제거에도 보호 규칙이 유지되게 합니다.
- 완료 조건: 비관리자 변경 거부, 위임 범위 초과 거부, 마지막 관리자 보호의 동시성, 감사 기록과 실제 변경의 일치를 자동 검증합니다. local/test 계정이 운영에 생성되지 않음을 확인합니다.

### 7단계: 프런트엔드 권한 조회 연동 — 중간

- 선행: 4단계. 관리자 화면은 6단계 완료 후 연결합니다.
- 작업: 내 사용자 정보·유효 권한 조회 API 계약을 정하고 React의 메뉴·버튼 표시와 401/403 처리를 연결합니다. UI 권한 요약은 편의 정보이며 서버 인가를 대체하지 않습니다.
- 완료 조건: 로그인 후 권한 표시, 권한 없는 화면 처리, 토큰 만료와 실행 중 권한 회수에 대한 UI 동작을 검증합니다. UI를 우회한 직접 API 요청도 거부됨을 확인합니다.

### 8단계: 측정에 따른 선택적 TTL 캐시 도입 — 후순위

- 선행: 4~6단계 및 실제 권한 조회 부하 측정. 성능상 필요가 없으면 도입하지 않습니다.
- 작업: 회수 지연을 허용할 권한만 선정하고 TTL, 캐시 키, 다중 인스턴스 동작, 무효화 및 장애 시 처리 정책을 정합니다. 민감한 작업은 강한 통제 경로를 유지합니다.
- 완료 조건: TTL 만료 경계, 역할 변경·계정 비활성화, 인스턴스 간 차이, 캐시 장애에서 정책이 유지됨을 검증하고 회수 지연과 성능 개선을 측정합니다. 캐시로 2단계의 계정 상태 검증을 약화하지 않습니다.

각 단계의 검증은 해당 구현과 함께 수행하고 실제 결과를 기록합니다. 스키마 정의 후의 진행 순서에 따라 권한 판정 서비스와 단위 테스트를 구현했습니다. API·DB 연결과 해당 통합 검증은 아직 수행하지 않았습니다. 구현 상태는 관련 기준 문서에 반영하되, 제안 단계의 상세 설계를 중복 작성하지 않습니다.

## DTO·record 타입 규칙 변경 — 2026-11-06

- 사용자 결정: DTO·record 필드는 원시 타입 대신 래퍼 타입을 사용합니다. `AuthUser.enabled`·`AuthRole.systemRole`은 `Boolean`, `TokenResponse.expiresIn`·`AuthService.IssuedToken.expiresIn`은 `Long`으로 변경했습니다.
- `AuthUser.xml` 생성자 매핑은 `Boolean`에 맞춰 MyBatis 별칭 `boolean`으로 변경했습니다. 앞선 `_boolean` 수정은 당시 원시 타입 모델에 맞춘 기록이며 현재 모델에는 적용하지 않습니다.
- 로그인·인가 서비스는 `Boolean.TRUE.equals(user.enabled())`로 확인하며 null 활성 상태는 비활성으로 취급해 거부합니다. 자동 언박싱하지 않습니다.
- 래퍼 타입은 null을 표현하기 위한 것으로 필수값 검증을 대체하지 않습니다. DB의 `enabled`, `system_role` NOT NULL 제약과 API 응답 필수값 정책은 유지합니다.
- 검증: JDK 21·Maven 3.9.11의 `mvn test` 전체 19개 통과. 로그인·인가에서 null 활성 상태를 거부하는 사례와 기존 DB 생성자 매핑을 포함합니다. `git diff --check`도 통과했습니다.

## API·서비스·비동기 인가 TODO — 2026-11-04

아래는 논의한 적용 방안을 구현·검증하기 위한 미완료 목록입니다. 현재 완료된 권한 판정 서비스 단위 검증과 구분하며, 인터셉터·Method Security·비동기 실행기를 이미 적용했다는 의미는 아닙니다. 각 항목은 구현과 검증 결과를 확인한 뒤 완료로 변경합니다.

### API 정책 선언과 공통 인가 — 최우선

- [x] API 공개 여부와 비공개 API의 권한 요구 수준(인증만 필요·세부 권한 필요)을 선언하는 어노테이션을 정의하고 실제 DB 권한 판정에 연결한다.
- [x] JWT 필터의 인증 등록 후 MVC `HandlerInterceptor`에서 실제 `HandlerMethod`의 정책을 읽어 공통 검사하도록 구성한다. 사용자명은 요청 본문 대신 서버 인증 정보에서 가져온다.
- [x] 공개 API는 인증을 요구하지 않는다. 비공개 API는 먼저 인증을 확인하고 없으면 401로 처리한다. 인증만 필요한 API는 활성 계정이면 허용하고, 세부 권한이 필요한 API는 추가로 `AuthorizationService.requirePermission`을 호출한다. 인증 후 세부 권한 부족은 403으로 처리한다. 실제 DAO·서비스 연결은 완료되어 있다.
- [x] 정책 어노테이션 누락은 인증 여부와 관계없이 기본 거부한다. 컨트롤러 메서드 안에서 판정을 수기로 반복하지 않는다.
- [x] Spring Security 필터 체인과 MVC 검사 사이의 책임을 정하고, 401·403 및 조회 장애 응답을 일관되게 처리한다. 공개 경로도 HTTP 메서드를 구분하고 미등록 경로를 포괄 허용하지 않는다.

### MVC 예외 경로와 디스패치 — 최우선

- [x] `HandlerMethod`가 아닌 핸들러를 일괄 허용하지 않고 정적 리소스·프레임워크 경로별 정책을 명시한다. React 공개 파일과 비공개 사용자 이미지 접근 경로를 분리한다.
- [ ] 비공개 이미지는 공개 정적 경로로 우회 접근할 수 없도록 보호 다운로드 API 또는 제한된 저장소 접근 방식을 정한다.
- [x] 내부 `DispatcherType.ERROR` 처리와 직접 `/error` 요청을 구분한다. 원래 오류가 인가 오류로 덮이거나 오류 처리가 반복되지 않는지 검증한다.
- [x] 허용 출처·메서드·헤더의 정상 CORS preflight를 처리하고 실제 API 요청에는 인증·인가를 적용한다. 모든 OPTIONS 요청을 일괄 허용하지 않는다.
- [x] GET의 HEAD 처리, 미등록 경로, MVC 비동기 재디스패치의 정책과 인터셉터 재실행 동작을 정의하고 우회·중복 부작용을 검증한다.

### 서비스 경계의 Method Security — 높음

- [ ] 특별 관리 서비스를 한곳에 모으기보다 각 업무 모듈의 보호 대상 공개 진입점을 식별한다. HTTP 외 호출 경로가 있는지도 확인한다.
- [ ] `@EnableMethodSecurity`, `@PreAuthorize`와 인증 정보를 해석하는 연결 컴포넌트의 적용을 구체화한다. 연결 컴포넌트는 권한 부족을 거부하고 조회 장애를 정상 허용이나 단순 권한 부족으로 숨기지 않는다.
- [ ] 같은 클래스의 `this` 호출은 프록시를 우회하므로 보호 진입점을 별도 Spring 빈으로 분리하는 등 호출 구조를 정한다. 프록시가 가로챌 수 없는 메서드도 검증한다.
- [ ] REST·다른 서비스·메시지 소비자·예약 작업에서 동일한 보호 진입점을 호출하는 경우를 검증한다. 시스템 작업은 명시적인 주체와 허용 범위를 정의한다.
- [ ] API 접근 권한과 리소스 소유권·공유 범위를 분리해 검사한다. 사전 어노테이션 검사만으로 권한 회수와 DB 변경의 원자성을 보장하지 않으며, 민감한 변경은 트랜잭션 실행 게이트를 별도로 적용한다.

### 같은 프로세스의 중첩 비동기 인증 전달 — 높음

- [ ] 공용 비동기 실행기를 `DelegatingSecurityContextAsyncTaskExecutor` 등으로 감싸 작업 제출 시점의 `SecurityContext`를 전달한다. Spring 빈의 수명 주기로 실행기 시작·종료도 관리한다.
- [ ] `@Async`에 실행기 이름을 명시하고 `CompletableFuture`에도 보안 실행기를 전달한다. 필요한 실행 API에 맞는 래퍼 타입을 선택한다.
- [ ] 작업 A가 작업 B를 다시 비동기로 제출하는 모든 단계에서 동일한 전달 규칙을 적용한다. `new Thread`, 실행기를 생략한 `CompletableFuture`와 commonPool 사용으로 전달이 끊기는 경로를 점검한다.
- [ ] 작업 실행 후 컨텍스트 정리·복원을 검증한다. 정상 종료·예외·취소 및 스레드 재사용에서 다른 사용자의 인증 정보가 남지 않는지 확인한다. 스레드 풀에 전역 상속형 컨텍스트를 설정하는 방식으로 대체하지 않는다.
- [ ] 최초 작업에 인증 정보가 없으면 래퍼가 인증을 생성하지 않는다는 전제로 처리한다. 누락 시 실패 처리와 시스템 주체 작업의 별도 실행 규칙을 정한다.
- [ ] 컨텍스트 전달은 제출 시점의 신원 전달이며 최신 권한 보장이 아님을 명시하고, 실제 실행 시 계정 활성 상태·DB 권한을 다시 확인한다.
- [ ] 사용자 A/B 교차 실행, 중첩 제출, 인증 없는 제출, 권한 회수·계정 비활성 후 실행, 작업 실패 뒤 스레드 재사용을 자동 검증한다. Spring MVC 비동기의 컨텍스트 전달도 사용하는 반환 타입별로 별도 확인한다.

### 큐·장기 실행 작업의 실행 주체 — 높음

- [ ] 작업 기록에 작업 ID·요청 사용자 식별자·대상 리소스·작업 종류를 저장하는 계약을 정의한다. 사용자 식별자 형식은 불변 ID 전환 여부와 맞춘다.
- [ ] 사용자 JWT나 `SecurityContext` 전체를 작업 메시지에 저장하지 않는다. 워커는 검증된 작업 기록에서 주체를 확인하고 실행 시 계정·권한·리소스 범위를 다시 검사한다.
- [ ] Method Security를 사용하는 워커에서 필요한 `Authentication`을 신뢰할 수 있는 기록과 최신 계정 정보로 구성하고 작업 범위에서 설정·정리하는 방식을 정한다. 메시지의 임의 사용자명만으로 인증 주체를 만들지 않는다.
- [ ] 등록·대기·실행·완료 단계에서 권한 회수가 발생했을 때 재검사·중단·완료 허용 기준을 정한다. 장기 작업 중 재검사 시점과 외부 호출·파일 저장의 취소·보상 정책도 정의한다.
- [ ] 워커 내부의 중첩 비동기 작업도 보안 실행기를 사용하고, 재시도·재시작 후에도 주체 복원과 최신 권한 검사가 유지되는지 검증한다.
