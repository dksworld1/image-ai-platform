# 4단계: 이미지 수집과 업로드

2026-11-13 후속: 사용자 요청으로 [프런트 업로드 모달](../front/design.md#이미지-업로드-버튼모달--2026-11-13)을 구현했습니다. 아래 프런트 취소 설명은 이전 이력입니다. 기존 단건 API를 순차 호출하며 이번 UI 작업에서 백엔드 계약은 변경하지 않았습니다.

- 상태: 일반/수정 업로드·버전·작업 이력·원본/썸네일 조회 구현, 실제 DB 미적용·기타 수집 후속
- 선행 단계: 1, 2, 3단계
- 관련 문서: [제품 개요](../../product/project-overview.md), [아키텍처](../../architecture/architecture.md)

## 목표

사용자가 이미지와 메타데이터를 데이터셋에 안전하고 추적 가능한 방식으로 추가하도록 합니다.

## 핵심 개념과 원리

- 업로드는 전송과 검증을 거쳐 데이터셋 항목으로 등록되는 하나의 수명 주기입니다.
- 부분 실패와 재시도를 고려하고, 중복 등록 정책을 명시합니다.
- 파일 검증은 이름이나 브라우저가 제공한 MIME 형식만 신뢰하지 않고 실제 콘텐츠와 제한을 확인해야 합니다.
- 이미지 바이너리 저장과 검색 가능한 메타데이터 관리는 서로 다른 책임으로 설계할 수 있습니다.

## 설계 범위

입력 경로, 허용 형식·크기, 대량 업로드, 중복 처리, 저장 위치, 접근 제어, 보존·삭제, 실패 복구를 정합니다.

## 결정 기록

- 2026-11-12: [ADR-036](../../decisions/ADR-036-dataset-image-upload.md)에 따라 로컬 파일 저장·원본명/경로 DB 메타데이터·데이터셋 내 원본명 중복 409를 구현했습니다. 업로드 기능 권한과 ACTIVE 공간/멤버십·운영자 또는 데이터셋 생성자 조건을 서비스와 실제 INSERT에서 확인합니다. 같은 원본명은 다른 데이터셋에 허용합니다. 파일·메타데이터 실패 정리와 등록 목록 API도 제공합니다.
- 사용자 확인: 파일은 로컬, 업로드 허용은 운영자/데이터셋 생성자. 이후 프런트 화면 구현을 취소하여 관련 컴포넌트·API 클라이언트·스타일을 제거했습니다. 향후 UI에서 성공·실패 목록을 구성할 수 있도록 단건 상태 계약만 유지합니다.
- 설정: 사용자 후속 지시에 따라 저장 루트·파일당 최대 용량·multipart 설정은 application.yaml에 직접 작성합니다. DB 접속 YAML import는 유지합니다. 추가 설정 후보는 [agent의 제안](../../agent-suggestions.md)에만 기록하며 승인 없이 확장하지 않습니다.

## 이번 구현 검증

2026-11-13 이미지 권한 분리: [ADR-040](../../decisions/ADR-040-image-permissions.md)에 따라 이미지 read·upload·update를 서비스 @PreAuthorize에서 분리하고 delete 카탈로그를 등록했습니다. 이미지 대상 판정과 실제 쓰기 SQL을 데이터셋 삭제 조건에서 독립시켰으며 선택 목록도 image-targets API로 분리했습니다. 이름이 없는 수정 업로드는 신규 등록이므로 upload도 검사합니다. 데이터셋 삭제는 이미지 권한 없이 기존 삭제 권한으로 처리합니다.

이번 변경은 Java 21에서 이미지 권한 분리 2개·데이터셋 삭제 2개·공통 카탈로그 1개·local admin seed 1개만 선별 실행하여 총 6개 통과했습니다. 이미지 read만 허용/데이터셋 read만 거부, 수정 전용 사용자의 기존 이름 교체 및 신규 이름 거부, upload만 있는 사용자의 수정 거부, 데이터셋 삭제·하위 이미지 이력 유지, seed 재실행·감사 값 보존을 확인했습니다. 실제 DB·서버는 변경하지 않았습니다.

2026-11-13 버전·이력·원본 확인: [ADR-039](../../decisions/ADR-039-image-version-history.md)에 따라 V20 DDL·공통 V21 BASELINE 이관을 구현했습니다. 일반 업로드 중복 거부를 유지하고 수정 모드에서 이전 버전 삭제 표시·새 파일 등록·버전 증가·CREATE/UPDATE/DELETE 이벤트를 저장합니다. 데이터셋 삭제 이벤트도 남기며 원본 조회는 읽기 권한·멤버십을 검사합니다.

Java 21에서 업로드 6개·삭제 2개·목록 개수 1개·기존 데이터 이관/local seed 2개를 선별 실행해 총 11개 통과했습니다. 원본 조회와 동시 교체 검증을 추가한 뒤 업로드 7개를 재실행해 통과했습니다. 이전 파일/행 보존·활성 개수·작업자·연속 버전·잘못된 파일/권한 거부·이력 저장 실패 시 상태/파일 롤백·삭제 후 이력 보존·BASELINE 감사 정보와 멱등 적용을 확인했습니다. 전체 테스트·실제 사용자 DB 적용·서버 재시작은 수행하지 않았습니다.

최종적으로 교체 원본을 기존 이미지와 다른 바이트로 바꾼 관련 테스트 1개를 재실행해 새 원본 조회·이전 파일 보존을 확인했습니다.

2026-11-13: 썸네일 백엔드를 구현했습니다. 생성 크기·비율·작은 이미지 확대 금지, 투명도·원본 보존, 조회 권한·데이터셋 격리, 기존 이미지의 null URL/404, DB 실패 시 두 파일 정리를 포함해 Java 21의 DatasetImageUploadTest 4개를 선별 실행하여 통과했습니다. [ADR-038](../../decisions/ADR-038-image-thumbnails.md)을 따릅니다. 실제 사용자 DB 적용·서버 재시작·프런트 변경은 하지 않았습니다.

Java 21에서 업로드 관련 3개·local 권한 seed 1개를 선별 실행해 통과했습니다. 실제 PNG 바이트·원본명·시각/작업자 저장, 동일 데이터셋 중복 거부와 다른 데이터셋 동일명 허용, 콘텐츠·권한·탈퇴 거부, DB 실패 시 파일 정리를 확인했습니다. 저장 SQL·YAML 크기 제한 정리 후 업로드 3개만 재실행해 통과했습니다. 취소한 프런트는 기존 상세 화면으로 빌드 성공을 확인했습니다. 실제 사용자 서버·DB에는 적용하지 않았으며 전체 테스트는 실행하지 않았습니다.

- 현재: 로컬 파일 + DB 메타데이터, multipart 단건 요청. 프런트 구현은 취소.
- 미결정: 수집 커넥터 및 입력 원천 범위
- 현재: 데이터셋 내 원본명 일치만 중복으로 거부. 자동 재시도 없음. 같은 이름의 다른 데이터셋 등록은 허용.
