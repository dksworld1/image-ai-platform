# 데이터셋 업무 개발 작업계획서

- 상태: 목록·공간별 독립 생성·데이터셋 삭제 API 구현, 삭제 UI·이미지·상세·수정 후속
- 종류: 작업계획
- 작성일·갱신일: 2026-11-10
- 현재 완료 범위: DATA-001 다중 공간 생성과 DATA-002 가입 공간 통합 목록
- 다음 지시 대상: 상세·수정·삭제 정책과 관리 화면
- 후속 설계: [워크스페이스 가입 승인과 데이터셋 접근 범위](workspace-design-proposal.md) — 검토 중, 구현 승인 전
- 2026-11-11 산출물: [워크스페이스 테이블 정의](../db-schema/tables/workspace/README.md) — V10·local admin 공통 공간 seed 구현, dataset 공간 FK는 전환용 nullable. 관련 테스트 3개 통과. 관리 화면·업무 API·실제 DB 적용은 후속
- 기능 기준: [기능 정의서](../product/functional-specification.md)의 DATA-001~009

## 목적과 사용 방법

사용자가 작업 목록과 결과를 보며 개발 순서·범위를 지시하는 관리 문서입니다. 문서 작성은 아래 작업 전체의 구현 착수를 의미하지 않습니다. 지시한 작업과 그에 필요한 범위 안에서 진행하며, 아직 확정하지 않은 정책을 임의로 확정하지 않습니다.

| 지시 예시 | 처리 범위 |
|---|---|
| “DS-01 진행. 우선 상세안 보여줘” | 생성 요구사항을 정리하고 검토할 문서를 제시 |
| “DS-01에서 이름 필수, 설명 선택으로 확정” | 해당 결정을 기능 정의서와 관련 설계에 반영 |
| “DS-04 구현해” | 선행 조건을 확인하고 생성 백엔드 구현·테스트·문서 갱신 |
| “DS-07은 화면만 먼저 보여줘” | 생성 페이지의 화면 초안을 제시. API 연동 완료로 기록하지 않음 |
| “DS-08까지 현황 알려줘” | 해당 작업들의 상태, 결과 위치, 검증과 남은 사항 보고 |
| “DS-10 보류하고 생성 화면부터 마무리” | 삭제 정책 작업을 보류하고 생성 관련 남은 작업 우선 진행 |

작업 상태는 `미착수`, `설계 중`, `구현 중`, `검토 대기`, `완료`, `보류`로 관리합니다. 사용자 결정이 필요한 작업은 해당 결정을 받은 뒤 의존 작업을 진행합니다. 상태만 바꾸지 않고 완료 근거와 다음 행동을 함께 기록합니다.

## 현재 기준선

- 이미지 업로드(2026-11-12): 서버 단건 업로드·데이터셋별 원본명 중복 검사·로컬 파일/DB 메타데이터·등록 목록을 구현했습니다. [이미지 업로드 단계](backend/stage-04-ingestion-upload.md)와 [ADR-036](../decisions/ADR-036-dataset-image-upload.md)을 따릅니다. 사용자 요청으로 프런트 업로드 구현은 취소했으며 현재 상세 모달에 추가 화면은 없습니다. 운영자/생성자라도 활성 멤버십과 업로드 기능 권한이 필요합니다. 실제 DB 미적용입니다.

- 목록 삭제 UI 후속: 행·전체 선택 체크박스와 선택 삭제 버튼, 기본 확인창·부분 실패 결과를 구현했습니다. 기존 단건 삭제 API를 재사용하며 상세 모달·이미지 삭제·배치는 추가하지 않았습니다. 프런트 빌드·격리 브라우저 흐름 확인 통과. DS-12 중 목록 삭제는 완료, 상세 삭제 모달은 후속입니다.

- 데이터셋 삭제(2026-11-11): DS-10의 기능 권한·ACTIVE 멤버십·공간 운영자/데이터셋 생성자 정책과 DS-11의 현재 dataset 행 삭제 백엔드를 구현했습니다. [ADR-035](../decisions/ADR-035-dataset-deletion-authorization.md), [API](../api/api.md#데이터셋-삭제)를 따릅니다. DS-12 UI와 이미지 삭제·배치는 사용자 지시로 이번 범위에서 제외합니다. 삭제 관련 3개 테스트 통과, 실제 사용자 데이터 삭제는 하지 않았습니다.

- 최신 변경(2026-11-11): [ADR-034](../decisions/ADR-034-independent-dataset-creation.md)에 따라 여러 공간 선택은 공간별 독립 데이터셋 생성입니다. 각 ID·귀속 공간은 분리되고 전체 생성은 한 트랜잭션입니다. local 미귀속 과거 데이터만 첫 번째 공통 공간에 V17로 배정하며 기존 귀속은 유지합니다. 아래 공유 방식 구현 기록은 이전 이력입니다.

- 2026-11-11 후속: 목록 GET /api/datasets, 가입 공간 GET /api/workspaces, workspaceIds 필수 다중 공간 생성과 체크박스 드롭다운을 구현했습니다. 공간 연결은 V11·V12·V13 및 [ADR-033](../decisions/ADR-033-dataset-multiple-workspaces.md)을 따릅니다. DS-05·06은 목록·메타데이터 상세 완료·이미지 후속, DS-07은 생성·목록 연결 완료·상세 이동 후속입니다. 변경 관련 백엔드 10개·프런트 3개·빌드·격리 브라우저 흐름 검증 통과. 실제 DB 적용과 관리 화면은 후속입니다. 아래 이전 생성 전용 기준선과 구분합니다.

- 2026-11-10: 사용자 요청으로 진행 중이던 생성자 기준 목록 프런트·백엔드 구현을 롤백했습니다. 목록은 미구현 상태를 유지하며, 여러 워크스페이스 가입·관리자 승인·같은 공간 데이터셋 조회 요구를 먼저 설계합니다. DS-02·03에서 공간·멤버십·기존 데이터 귀속을 확정한 뒤 DS-05·06을 진행합니다. 제안 상세는 [워크스페이스 설계 제안](workspace-design-proposal.md)에 기록하며 아직 현재 API·스키마 계약으로 채택하지 않았습니다.

- 데이터셋 생성·목록·상세·수정·삭제와 이미지 관리 기능 목록은 확정되어 있습니다.
- [화면 스토리보드 v2](../storyboards/dataset-management/README.md)는 목록·상세·생성 페이지 3개와 수정·삭제 모달 2개를 관리합니다. 생성은 별도 페이지와 데이터셋 > 데이터셋 생성 메뉴로 확정했으며, 나머지 배치·세부 동작은 설계 초안입니다.
- 생성 백엔드는 app V6·도메인·DAO·서비스·POST /api/datasets를 구현했습니다. 활성 로그인 사용자 기준으로 UUID·공통 타임스탬프·작업자를 서버에서 기록합니다. 프런트 생성 폼도 저장에 연결했습니다. 목록·상세가 아직 없어 성공은 생성 이름·ID 표시와 폼 초기화, 취소는 시작 화면(`/`) 이동으로 제공합니다. [ADR-030](../decisions/ADR-030-dataset-creation-contract.md)을 따릅니다.
- 기존 인증·서비스 권한 검사와 로그인 세션을 사용합니다. 데이터셋별 소유·공유 정책은 미정입니다.
- 모든 신규 테이블에 [공통 스키마 규칙](../db-schema/schema-rules.md)을 적용합니다. 시스템 작업자는 문자열 `'0'`, 사용자 작업자는 서버에서 확인한 내부 user_key입니다. 로그인 user_id·실명 username과 구분하며 생성자는 소유 정책을 대신하지 않습니다. [ADR-031](../decisions/ADR-031-user-identity-fields.md)을 따릅니다.

## 개발 묶음과 확인할 결과

| 묶음 | 작업 | 사용자 확인 결과 | 선행 조건 |
|---|---|---|---|
| 1. 생성과 기본 조회 | DS-01~07 | 메뉴에서 생성 페이지로 이동해 저장한 데이터셋을 상세·목록에서 확인 | 생성 입력과 접근 정책, 데이터·API 계약 확정 |
| 2. 정보 수정 | DS-08~09 | 상세에서 이름·설명을 수정하고 결과 확인 | 생성·조회 기능과 수정 권한·입력 규칙 |
| 3. 데이터셋 삭제 | DS-10~12 | 삭제 영향을 확인하고 정책에 따라 데이터셋 삭제 | 삭제·보존 정책 확정 |
| 4. 이미지 관리 | DS-13~16 | 이미지 탐색, 메타데이터 수정, 이미지 삭제 | 이미지 모델·저장소·제공 방식과 수집·업로드 단계 연계 |

우선 묶음 1을 진행합니다. 목록·상세는 생성 결과를 실제로 확인할 수 있는 최소 범위부터 구현합니다. 이미지가 아직 없는 단계에서는 빈 상태를 표시하며 가짜 이미지를 실제 조회 결과처럼 넣지 않습니다. 이미지 반입(ING), 전처리, 레이블링, 클러스터링, 플러그인 처리는 별도 업무 계획을 따릅니다.

## 구현 경계와 문서 관리

### 생성 입력 항목 확장 원칙 — 2026-11-10 확정

생성 입력 항목은 향후 추가될 수 있음을 전제로 구현합니다. 현재 이름·설명만으로 폼 구조와 높이를 고정하지 않습니다.

- 페이지 본문에 입력 필드를 세로로 배치하고 내용이 늘어나면 페이지 스크롤로 접근할 수 있게 합니다. 고정 높이·절대 좌표에 의존해 입력란이나 생성·취소 버튼이 가려지는 구조를 사용하지 않습니다.
- 각 필드의 값·레이블·검증·오류 표시를 구분하고, 생성 요청과 성공·실패 처리는 폼 제출 흐름에서 관리합니다. 새 필드가 생겨도 메뉴·페이지 이동과 제출 흐름을 다시 설계하지 않도록 합니다.
- 업무상 관련 있는 필드가 실제로 추가되면 해당 그룹을 구분합니다. 미래 필드용 빈 영역·단계·탭을 미리 만들거나 현재 기능에 입력 항목을 임의로 추가하지 않습니다.
- 프런트 요청 타입과 백엔드 DTO·검증은 명시적으로 선언합니다. 항목을 추가할 때 API 계약·저장 모델·테이블·화면·동작 테스트 중 영향받는 부분을 함께 갱신합니다. 선택 입력의 미입력·기본값 정책과 기존 요청 호환성도 해당 변경에서 결정합니다.
- 입력 항목 추가를 위한 범용 동적 폼 엔진·메타데이터 관리 테이블·공통 프레임워크는 도입하지 않습니다. 기존의 작은 컴포넌트와 명시적 타입으로 필요한 확장만 반영합니다.

DS-03·04·07의 설계·구현·검증에 이 원칙을 적용합니다. DS-07 완료 시 현재 필드의 화면 조작과 좁은 화면·확대·스크롤에서 입력 및 실행 버튼 접근을 확인합니다. 검증을 위해 제품 화면에 가짜 필드를 추가하지 않습니다.

- 백엔드는 기존 `com.imageaiplatform.dataset`의 controller·service·dao·dao.impl·domain 역할을 따릅니다. 신규 업무는 app 데이터소스를 사용하며 인증·권한 모듈은 서비스 경계로 호출합니다.
- 프런트는 기존 레이아웃·로그인 세션·API 경계를 사용합니다. 데이터셋 진입점과 화면 이동은 업무에 필요한 범위로 추가하며 폐기된 DB 기반 메뉴 모듈을 복원하지 않습니다.
- API·테이블·권한 식별자는 DS-02·03에서 결정합니다. 이 계획서에서 미리 고정하거나 아직 없는 엔드포인트를 현재 API로 기록하지 않습니다.
- 스키마는 적용된 마이그레이션을 수정하지 않고 구현 시점의 다음 버전으로 추가합니다. 권한 행 등 DML은 DB별 seed에 두고 common/local 적용 범위를 구분합니다.
- 기능 동작에 필요한 변경과 검증을 각 작업에 포함합니다. 개발 도구·공통 프레임워크·부가 기능을 계획에 끼워 넣지 않으며 추가 제안은 [agent의 제안](../agent-suggestions.md)에만 기록합니다.
- 상세 목표·원리·완료 조건과 검증 근거는 [백엔드 3단계](backend/stage-03-datasets.md) 및 [프런트 단계](front/README.md)에 연결합니다. 중요한 구조 결정이 생기면 ADR을 추가합니다.

## 완료 판정과 결과 기록

각 구현 작업에서 실제 동작 테스트와 필요한 빌드 검증을 수행합니다. 마지막에 한꺼번에 검증하는 방식으로 미루지 않습니다. 백엔드는 저장소의 Java 21 Maven 절차, 프런트는 관련 자동 검증과 타입 검사·빌드를 따릅니다. 화면 작업은 배치와 실제 조작 흐름도 확인하며 실행하지 않은 검증은 미실행으로 표시합니다.

묶음 1의 사용자 확인 시나리오는 “로그인 → 데이터셋 대메뉴 → 데이터셋 생성 → 입력·생성 → 새 상세 → 목록에서 생성 결과 확인”입니다. 수정과 삭제도 각 묶음 완료 시 실제 API와 화면을 연결해 확인합니다. 코드 완료와 실제 DB 적용 여부는 구분합니다.

작업 완료 시 위 작업 목록 상태와 아래 결과 기록을 함께 갱신합니다. 진행 중에는 수행한 범위와 남은 조건을 기록하며 실제 결과가 없으면 완료로 표시하지 않습니다.

| 작업 ID | 상태 | 결과 문서·코드 | 검증 결과 | 사용자 확인 사항·다음 행동 |
|---|---|---|---|---|
| DS-01 | 설계 중 | 생성은 별도 페이지, 메뉴는 데이터셋 > 데이터셋 생성으로 확정. 스토리보드 v2·ADR-029 반영 | 페이지·메뉴 설계 반영. UI 검증은 DS-07 기록 참조 | 입력 규칙·중복 정책·이탈 정책 결정 필요 |
| DS-07 | 구현 중 | 메뉴·생성 폼·API 저장·성공 확인·실패 입력 유지 구현 | 프런트 14개 테스트·빌드 성공. Edge에서 요청 중·성공·실패 및 화면 크기 확인 | 목록·상세가 없어 현재 성공은 결과 표시, 취소는 시작 화면 이동 |

DS-04 생성 백엔드는 전체 57개 테스트가 통과했습니다. DS-07은 실제 API 호출·요청 중 입력 잠금·실패 시 입력 유지·성공 확인과 초기화까지 구현했습니다. 프런트 14개 테스트·빌드와 응답 대체를 사용한 브라우저 동작 검증이 통과했습니다. 목록·상세가 없어 DS-07의 전체 완료는 보류하며 저장 버튼은 현재 활성 입력 조건에 따라 동작합니다. 로컬·운영 DB에는 마이그레이션을 실행하지 않았습니다.

### 기본 원칙

기존 데이터셋은 파일 추가·교체·논리 삭제·설명 수정을 수행하는 현재 편집본입니다. 데이터셋 버전은 특정 시점의 전체 이미지·데이터 파일 구성과 당시 메타데이터를 고정한 스냅샷입니다. 개별 이미지·데이터 파일의 교체 버전과 데이터셋 전체 버전을 구분합니다.

버전마다 전체 구성 메타데이터를 저장하되 파일 바이트는 복사하지 않고 고정된 파일 버전 ID를 재사용합니다. 아티팩트셋을 다시 도입하는 설계가 아닙니다. 같은 파일 버전이 여러 데이터셋 버전에 포함되어도 실파일 하나를 참조할 수 있습니다.

확정된 버전의 ID·구성·당시 설명을 수정하거나 삭제하지 않습니다. 해당 버전이 참조하는 파일 행과 실제 파일도 물리 삭제하지 않습니다. 현재 데이터셋에서 논리 삭제한 파일이라도 과거 버전의 참조가 있으면 계속 보존합니다. 버전 기록의 보존과 파일 바이트의 보존은 개념적으로 다르지만, 초기에는 둘 다 보존해 계보와 재실행을 보장하는 방향입니다. 자동 파일 정리·버전 폐기 정책은 도입하지 않습니다.

### 논의한 스키마 초안

| 테이블 후보 | 역할·주요 필드 |
|---|---|
| dataset_version | version_id(PK), dataset_id(FK), version_number, name·description 스냅샷, change_note |
| dataset_version_image | version_id + image_id 복합 PK, original_filename·description 스냅샷 |
| dataset_version_file | version_id + file_id 복합 PK, original_filename·description 스냅샷 |

(dataset_id, version_number)는 고유합니다. 모든 테이블에 created_at·updated_at·created_by·updated_by를 필수로 둡니다. 연결한 image_id·file_id는 현재 최신 파일이 아니라 특정 파일 버전 행을 가리킵니다. 이름·설명처럼 같은 파일 행에서 바뀔 수 있는 정보는 버전 구성에 복사하여 과거 값을 유지합니다. 컬럼 상세 형식과 보전 FK·기존 삭제 API의 변경은 실제 구현 시 확정합니다.

초기 생성 방식은 명시적인 버전 생성 요청으로, 생성 트랜잭션이 성공하면 바로 확정하는 방식입니다. 별도 초안·공개 단계를 기본으로 요구하지 않습니다. 버전 번호는 1부터 증가하고 별도 UUID version_id를 실행 참조로 사용합니다. 이 문단은 논의 당시 초안이며, 이번 구현의 실제 컬럼·제약은 위 테이블 정의서를 따릅니다.

### 생성 알고리즘과 동시 변경

1. 활성 계정·기능 권한·대상 워크스페이스의 활성 멤버십을 검사합니다. 신규 권한의 구체적인 코드는 구현 설계에서 확정합니다.
2. app DB 트랜잭션에서 데이터셋 행을 잠급니다.
3. 해당 데이터셋의 현재 활성 이미지·데이터 파일 버전과 이름·설명을 읽습니다.
4. 데이터셋별 다음 버전 번호를 발급하고 dataset_version을 생성합니다.
5. 전체 구성 항목을 버전 연결 테이블에 저장하고 한 번에 커밋합니다.

파일 추가·교체·논리 삭제·설명 수정·데이터셋 메타데이터 수정도 같은 데이터셋 행을 먼저 잠가야 합니다. 이 규칙을 함께 적용해야 서로 다른 시점의 상태가 하나의 버전에 섞이지 않습니다. 잠금과 고유 제약으로 동시 번호 발급을 제어하고, 실패 시 전체 롤백해 부분 스냅샷을 남기지 않습니다. 이번 구현에서는 기존 이미지·파일 추가·교체·논리 삭제·설명 수정 경로가 같은 데이터셋 행을 잠그는 것을 확인했고, 버전 생성도 해당 잠금을 사용합니다. 데이터셋 이름·설명의 수정 API는 현재 제공하지 않으며 향후 추가 시 같은 규칙을 적용해야 합니다.

통신 재시도에 의한 중복 버전 생성을 막는 요청 ID 방식은 구현 시 검토할 선택사항입니다. 아직 멱등 요청 키·중복 방지 정책을 구현하거나 확정하지 않았습니다.

### 조회·복원과 삭제 목록

각 버전이 전체 구성 목록을 가지므로 특정 버전의 복원에 이전 버전이나 삭제 이벤트를 순서대로 적용할 필요가 없습니다.

```text
v1 = A1, B1, C1
v2 = A1, C1          # B 제외
v3 = A1, C1, D1      # D 추가
```

v3는 A1·C1·D1의 목록과 해당 파일 버전만으로 조회·실행 재현이 가능합니다. B1은 v3 복원에 필요하지 않지만 v1이 참조하므로 계속 보존합니다. v2에서 제외한 B1은 v3의 전체 목록에도 없으므로 별도 누적 삭제 목록이 필요하지 않습니다.

변경 내역은 두 버전의 목록을 비교하여 계산합니다. 새 ID만 있으면 추가, 이전 ID만 있으면 제외, 기존 파일의 버전 연결을 따라 같은 논리 파일의 ID가 바뀌었으면 교체입니다. 이름만으로 교체를 추측하지 않습니다. 같은 파일 ID라도 스냅샷 설명이 다르면 메타데이터 변경입니다. 삭제가 일어난 정확한 작업 이벤트와 행위자는 별도 기존 작업 이력의 책임이며 버전 차이만으로 추정하지 않습니다.

고정 버전 조회·실행 재현과 현재 편집본을 과거 상태로 되돌리는 기능은 구분합니다. 되돌리기를 제공하더라도 기존 확정 버전을 덮어쓰지 않으며, 현재 편집본 준비·수정·새 버전 생성은 아래 후속 구현으로 추가했습니다.

### 실행 입력 고정과 기존 삭제 정책

스테이지가 데이터셋을 입력받을 때는 변경 가능한 dataset_id만 기록하지 않고 접수 시 구체적인 version_id로 고정합니다. '최신 버전' 선택도 접수 순간 특정 ID로 해석하고 실행 중 다시 최신 목록을 읽지 않습니다. 버전이 없는 현재 편집본을 실행하는 처리와 변경사항 존재 시 안내·버전 생성 정책은 후속 UI·실행 설계에서 정합니다. 초기에는 명시적 버전 생성을 우선하며 자동 버전 생성은 확정하지 않습니다.

버전의 파일 조회는 현재 활성 목록 필터를 재사용하면 안 됩니다. 고정된 구성 연결을 통해 읽고, 현재 목록에서 논리 삭제된 과거 파일도 버전 권한 검사 후 접근할 수 있어야 합니다.

현재 데이터셋 삭제는 하위 이미지·데이터 파일 버전 행을 연쇄 삭제합니다. 버전 참조 보호를 적용할 때 기존 삭제 API와 FK를 반드시 조정해야 합니다. 버전이 존재하는 데이터셋·버전 참조 파일의 물리 삭제를 차단하고, 과거 버전 조회에 필요한 부모 정보도 유지해야 합니다. 이번 구현에서 버전 존재 시 데이터셋 삭제를 409로 차단하고, V27의 FK로 버전·원본 파일 행에 대한 삭제 연쇄를 차단했습니다. 실제 파일의 자동 정리 경로는 제공하지 않습니다.

### 비용 판단과 대안

| 방식 | 저장 비용 | 특정 버전 조회·복원 |
|---|---|---|
| 전체 목록 스냅샷 — 채택 | 매번 전체 구성 메타데이터 저장 | 해당 버전만 조회 |
| 변경분만 저장 | 바뀐 항목만 저장 | 기준 상태부터 추가·교체·삭제 적용 필요 |
| 주기적 스냅샷 + 변경분 | 중간 수준 | 가까운 스냅샷과 이후 변경분 조회 |

현재 논의 규모는 약 200개 항목입니다. 한두 파일만 변경되어도 약 200개 메타데이터 행을 저장하지만 파일 바이트는 재사용합니다. 1,000개 버전이면 약 20만 구성 행이며, 실제 저장 크기는 컬럼·인덱스·설명 길이에 따라 달라집니다. 이 수치는 규모 예시이며 부하 측정 결과가 아닙니다.

초기에는 구성 메타데이터 중복보다 독립 조회·복원·계보 보전과 단순한 구현을 우선합니다. 항목 수·버전 생성 빈도가 크게 늘고 실제 측정으로 문제가 확인되면 변경분·혼합 방식을 별도로 검토합니다. 이번에 미리 구현하지 않습니다.

### 후속 구현 완료 조건

- 파일 교체·삭제·설명 변경 후에도 이전 버전의 구성·내용·당시 설명이 유지됩니다.
- 이전 버전 목록을 읽지 않고 임의의 확정 버전을 조회·재현할 수 있습니다.
- 동시 편집·버전 생성에서 일관된 스냅샷과 고유한 버전 번호를 보장합니다.
- 생성 실패 시 불완전한 버전·구성 행이 남지 않습니다.
- 버전 참조가 있는 파일·데이터셋의 삭제를 차단하고 논리 삭제된 파일도 과거 버전에서 읽습니다.
- 실행은 접수 시 고정한 버전만 사용합니다.

위 항목 중 스냅샷 보전·동시 생성·롤백·참조 삭제 차단·과거 파일 다운로드는 아래 테스트로 확인했습니다. 실행 입력 바인딩은 후속이며 현재 편집본 되돌리기는 아래 후속 구현으로 추가했습니다.

### 버전 관리 구현 결과 — 2026-11-23

기존 관리 화면의 버전 관리 탭에서 변경 설명 입력·수동 생성·최신순 목록·과거 버전 상세·고정 파일 다운로드를 제공합니다. 전체 파일 메타데이터를 한 app 트랜잭션에서 저장하고 실파일은 재사용합니다. 생성에는 dataset:version:create와 기존 관리 범위, 조회·다운로드에는 dataset:version:read 및 활성 멤버십이 필요합니다. local admin에만 새 권한을 자동 연결합니다.

검증: DatasetVersionTest 5개와 기존 DatasetDeletionTest·DatasetFileTest·DatasetImageUploadTest를 포함해 백엔드 선별 26개 통과. 프런트 빌드와 Node 테스트 34개 통과. Chromium에서 응답 대체 방식으로 목록/상세 이동, 고정 다운로드, 중복 클릭 억제, 생성 중 선택 차단, 권한 오류 시 입력 유지, 조회 재시도·탭 이동을 확인했습니다. 모바일 표가 사라지는 레이아웃을 수정했고 40개 버전·200개 항목의 표 내부 스크롤·컬럼 키보드 조절·짧은 창도 검증했습니다. 실제 로컬 기동과 V27 적용·헬스 UP·version-targets 200 결과는 운영 문서에 기록합니다. 이 문단의 검증은 초기 버전 관리 구현 결과이며 현재 편집본 준비는 아래 후속 구현을 따릅니다. 실행 바인딩은 후속입니다.

### 과거 버전으로 편집 시작 구현 — 2026-11-23

사용자 지시로 ‘v5 구성으로 현재 편집본 준비 → 필요한 파일 변경 → 다음 번호가 v10이면 v10 생성’ 흐름을 추가했습니다. [ADR-053](../decisions/ADR-053-edit-from-dataset-version.md), [API](../api/api.md#과거-버전으로-편집-시작--2026-11-23)를 따릅니다.

- 기준 버전과 같은 데이터셋의 공유 편집본 전체를 교체하며 별도 개인 브랜치는 만들지 않습니다.
- 전체 파일 검증 후 dataset 행 잠금 안에서 현재 파일 논리 삭제·기준 파일 ID 재활성화·당시 설명·이름 적용·이력 기록을 한 번에 커밋합니다. 실패 시 전부 롤백합니다.
- 파일 바이트·저장 경로·썸네일·확정 버전은 변경하지 않습니다. 적용 중 새 버전을 만들지 않고 base_version_id를 추가하지 않습니다.
- 빈 기준 버전도 적용할 수 있습니다. 이후 파일 수정과 새 버전 생성은 기존 기능을 사용하며 전체 버전 번호는 계속 증가합니다.
- 화면에서 공유 편집본 교체를 확인하고 성공 후 파일 편집 진입점을 제공합니다. 권한은 version:restore + version:read + 기존 관리 범위입니다.

검증: DatasetVersionTest 9개(v5→편집→v10, 과거 스냅샷·바이트 유지, 빈 기준 적용, 권한/범위 거부, 외부 트랜잭션 롤백·실파일 누락 시 편집본 보전 포함) 및 기존 이미지·파일·삭제 테스트를 합쳐 백엔드 선별 30개 통과. 프런트 테스트 36개와 빌드·백엔드 package 통과. Chromium 응답 대체로 적용 취소/확인·진행 중 잠금·새 버전 자동 생성 없음·파일 편집 후 v10 확정·v5 보전·실패 후 상태 유지와 기존 표 스크롤을 확인했습니다. 로컬 기동 시 V27을 유지하며 restore 권한 seed 2개를 적용했고 헬스 UP·인증된 선택 목록 200을 확인했습니다. 실제 로컬 편집본은 변경하지 않았으며 상세는 운영 문서를 따릅니다.

### 버전 관리 독립 페이지 — 2026-11-23

버전 관리 기능은 별도 메뉴 /datasets/versions로 분리하고 데이터셋 관리에는 이미지·데이터 파일 편집 탭만 유지합니다. 과거 버전 적용 후 편집 화면으로 이동하고 같은 데이터셋의 버전 페이지로 돌아오는 흐름을 제공합니다. 상세·검증은 [프런트 기록](front/design.md#버전-관리-독립-메뉴페이지--2026-11-23)을 따릅니다. 백엔드·DB 변경은 없습니다.

### 데이터셋·버전 관리 통합 — 2026-11-23

앞선 독립 메뉴 구성을 사용자 지시로 통합했습니다. 선택 데이터셋의 버전 목록부터 시작하고, 최초 버전 생성·기존 버전 상세·해당 버전 기반 인라인 파일 편집·신규 확정 순서로 진행합니다. [현재 화면 기준](front/design.md#데이터셋버전-관리-통합--2026-11-23)을 따릅니다. 기존 API와 권한을 재사용하며 백엔드·DB 변경은 없습니다.
