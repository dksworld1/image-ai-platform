# 프런트 단계: 화면과 사용자 흐름 설계

## 이미지 행 펼침 설명 편집 — 2026-11-13

이미지 목록의 설명 전용 컬럼을 제거했습니다. 요약 행의 일반 영역이나 원본 파일명을 클릭하면 바로 아래 전체 폭의 설명 편집 행을 펼치거나 접습니다. 키보드로 요약 행에서 Enter/Space를 사용해도 동작합니다. 체크박스·썸네일 버튼은 펼침에 영향을 주지 않으며 썸네일은 기존 원본 상세를 엽니다. 썸네일이 없는 이미지도 펼친 영역의 「원본 보기」로 원본을 확인할 수 있습니다.

사용자 후속 요청으로 설명 툴팁과 마우스 오버 안내를 제거했습니다. 설명 입력은 기본 접힘이며 행 클릭으로 펼치고 접어도 값·변경 강조·선택은 유지합니다. 실제 편집 시 자동 선택·행 강조와 기존 일괄 저장을 그대로 적용합니다. 업로드 모달도 파일명 클릭으로 설명을 펼치며 상단 안내를 표시합니다. 목록 최소 폭은 설명 컬럼 제거 후 1600px로 되돌렸습니다.

검증: 프런트 TypeScript·Vite 빌드 통과. 브라우저 직접 조작은 검증하지 않았습니다. 백엔드 소스 변경은 없으며 사용자 후속 지시에 따라 이번 프런트 수정에 대한 추가 재시작은 하지 않습니다.

## 업로드 설명 입력란 접기·펼치기 — 2026-11-13

일반/수정 업로드 모달의 파일별 설명은 기본으로 숨기고 파일명을 클릭하거나 키보드로 실행한 경우에만 펼칩니다. 다시 실행하면 접히며 입력값은 유지합니다. 모달 상단에 파일명 클릭 안내를 추가했습니다. 전송/완료 중에도 설명을 열어 확인할 수 있지만 textarea 편집 제한은 유지합니다. 프런트 TypeScript·Vite 빌드로 검증했습니다.

## 이미지별 설명·목록 편집·일괄 저장 — 2026-11-13

업로드 모달의 파일별 설명 입력과 목록의 설명 textarea를 추가했습니다. 최대 2,000자이며 빈 설명은 NULL입니다. 일반/수정 업로드 모두 파일별 입력값을 전송합니다. 목록 편집은 원본 응답과 별도 임시 값으로 관리하고 실제 변경 행은 색상으로 강조하며 자동 선택합니다. 체크 해제 시에도 강조·편집은 유지합니다. 원래 값으로 되돌린 행은 저장 대상에서 제외합니다. 표 최소 폭은 1800px이며 기존 내부 스크롤·컬럼 조절을 유지합니다.

「저장」 확인창은 미선택된 변경 행이 있을 때 `선택하지 않은 변경 행 N개의 편집 내용은 저장 후 초기화됩니다. 저장하시겠습니까?`로 안내합니다. 선택된 저장 행 수는 확인창에 표시하지 않으며, 미선택 변경이 없으면 일반 저장 확인만 표시합니다. 취소하면 편집·선택을 유지합니다. 선택된 실제 변경 행만 단일 PATCH로 전송하고 성공 시 응답의 수정 정보로 갱신하며 미선택 편집과 선택을 초기화합니다. 선택 변경이 0개이면 서버 요청 없이 확인 후 편집만 초기화합니다. 실패 시 모든 편집·선택을 유지하고 원인을 안내합니다.

저장 중 대상 전환·새로고침·업로드·삭제·추가 편집을 제한합니다. 설명 수정은 파일 버전을 증가시키지 않습니다. 대상 전환·새로고침 시 저장하지 않은 편집은 초기화되며 자동 임시 보존 기능은 없습니다. 화면 종료 시 요청을 취소하더라도 서버 처리가 끝났을 수 있어 재진입 시 목록 확인이 필요합니다.

검증: 프런트 TypeScript·Vite 빌드와 관련 테스트 3개를 선별 실행해 선택된 실제 변경 행 집계·빈 설명 정규화·업로드 파일별 설명·PATCH 계약·오류 처리를 확인했습니다. 브라우저 직접 조작은 검증하지 않았습니다. 백엔드 원자성 검증은 [수집 단계](../backend/stage-04-ingestion-upload.md#이번-구현-검증)에 둡니다.

## 이미지 버전 1 최초 등록일시 — 2026-11-13

이미지 목록에 「최초 등록일시」를 추가하고 기존 「등록일시」는 「현재 버전 등록일시」로 구분했습니다. firstRegisteredAt은 같은 이미지 계열의 버전 1 등록 시각이며 현재 버전의 createdAt과 별도입니다. 둘 다 현지 시간으로 표시합니다. 조회에서 이전 버전 연결을 따라 계산하며 파일명이 같아도 별도 신규 계열은 섞지 않습니다. 기존 데이터도 스키마 변경 없이 조회하고 알 수 없는 값은 `-`입니다. 표 최소 폭을 1600px로 조정하여 날짜 컬럼의 공간을 확보하며 기존 가변 폭·내부 스크롤·컬럼 조절을 유지합니다.

검증: 프런트 TypeScript·Vite 빌드 통과. 실제 브라우저 조작은 검증하지 않았습니다.

## 이미지 목록 버전 표시 — 2026-11-13

이미지 관리 표의 원본 파일명 다음에 「버전」 컬럼을 추가했습니다. 기존 API의 versionCount를 그대로 표시하며 최초 등록은 1, 교체 시 증가한 현재 활성 버전을 보여줍니다. 컬럼 비율 합계는 100%로 유지하며 내부 경계 조절·마지막 수정일시 오른쪽 핸들 없음 기준을 유지합니다. 백엔드 계약 변경은 없습니다. 검증은 프런트 TypeScript·Vite 빌드입니다.

## 데이터셋 상세의 이미지 관리 이동 — 2026-11-13

데이터셋 상세 조회 성공 시 모달 하단 오른쪽에 「이미지 관리」 버튼을 제공합니다. 조회한 datasetId를 인코딩한 `/datasets/images?datasetId=...`로 이동하여 해당 공간·데이터셋을 미리 선택합니다. 로딩·오류 상태에는 표시하지 않으며 이미지 화면의 조회 권한은 기존 서버 정책으로 검사합니다. 기존 행 우클릭 진입도 유지합니다. 프런트 TypeScript·Vite 빌드로 검증하며 별도 백엔드 변경은 없습니다.

## 이미지 행 선택·선택 삭제 — 2026-11-13

이미지 표 첫 컬럼에 개별/전체 선택 체크박스와 부분 선택 상태를 추가했습니다. 상단에 선택 건수·「선택 삭제」 버튼을 두고 미선택·삭제 중에는 실행을 막습니다. 확인창에 건수와 목록 제외·기록/파일 보관을 안내하며 취소하면 요청하지 않습니다. 단건 DELETE를 순차 호출하고 성공 행만 목록에서 제거하며 실패 행·선택·사유를 유지합니다. 전체 성공 시 빈 목록과 완료 건수를 표시합니다. 데이터셋/공간 변경과 재조회 시 선택·이전 삭제 결과를 초기화합니다.

삭제 중 대상 선택·조회·업로드·상세 열기를 막고 중복 실행을 제한합니다. 화면 종료 시 진행 중 요청을 취소하고 남은 전송을 중단하지만 서버 결과가 불명확할 수 있어 재진입 후 목록 확인이 필요합니다. 기존 그리드 폭·높이·스크롤과 내부 경계 조절은 유지하며 마지막 컬럼 오른쪽에는 핸들이 없습니다. 브라우저 직접 조작 검증은 수행하지 않았습니다.

프런트 TypeScript·Vite 빌드와 삭제 API 테스트 1개를 선별 실행해 경로 인코딩·인증·취소 신호·204 처리·401/403/404/500/통신 오류 및 자동 재시도 없음을 확인했습니다. 백엔드 관련 검증은 [수집 단계](../backend/stage-04-ingestion-upload.md#이번-구현-검증), 현재 계약은 [API](../../api/api.md#delete-apidatasetsdatasetidimagesimageid)를 따릅니다.

## 이미지 기능 권한 분리 연동 — 2026-11-13

이미지 관리의 데이터셋 선택 목록을 GET /api/datasets 대신 이미지 read 권한의 GET /api/datasets/image-targets로 변경했습니다. 선택에 필요한 이름·공간·ID만 받아 dataset:item:read 없이 이미지를 조회할 수 있습니다. 모달 안내도 일반 upload·수정 update, 신규 이름이면 upload 추가 검사로 맞췄습니다. 버튼 노출의 권한별 세분화 API는 추가하지 않았으며 최종 판정은 서버에서 수행합니다.

프런트 TypeScript·Vite 빌드와 대상 목록 API 관련 테스트 1개가 통과했습니다. 브라우저 조작 검증은 수행하지 않았습니다. 일반 사용자의 추가 수정·삭제 조건과 개별 삭제 UI는 이번 범위가 아닙니다.

## 이미지 수정 업로드·감사 컬럼·원본 상세 — 2026-11-13

이미지 목록에 등록자·수정자·수정일시를 추가했습니다. 등록자·수정자는 해당 버전의 현재 로그인 ID·실명을 함께 표시하고 없는 값은 `-`입니다. 내부 감사 키를 로그인 ID처럼 표시하지 않습니다. 마지막 컬럼은 수정일시로 변경하며 마지막 오른쪽 조절 핸들은 두지 않습니다.

「이미지 수정 업로드」를 클릭하면 「기존 파일을 덮어씁니다.」 확인창을 표시하고 확인한 경우 같은 업로드 모달을 수정 모드로 엽니다. 제목은 「이미지 수정 업로드」이며 모달 내부에도 경고·기존 버전 보관·미일치 이름 신규 등록 안내를 유지합니다. API에는 replaceExisting=true를 명시하고 순차 전송·파일별 결과·권한 오류 중단·완료 후 목록 갱신을 재사용합니다. 새 버전이 등록되므로 자동 재시도하지 않습니다.

썸네일 또는 원본 파일명 클릭 시 「이미지 상세」 모달에서 원본 콘텐츠를 표시합니다. 제목·원본명·현재 버전·형식·원본 용량을 보여주며 긴 이미지는 본문 가용 폭·60dvh 안에서 비율을 유지합니다. 시각 확인용 모달은 이미지 확인 목적상 가로 최대 1100px을 사용하는 예외입니다. 닫기·Escape·배경 클릭, 조회 로딩·오류·재시도를 제공하며 인증된 바이트의 object URL은 닫을 때 해제합니다. 썸네일 미생성 이미지도 원본명 버튼으로 원본을 볼 수 있습니다.

검증: TypeScript·Vite 빌드 통과. 프런트 이미지 관련 4개 테스트를 선별 실행해 일반/수정 업로드 URL·multipart·원본명·Bearer/취소 신호·원본 조회와 권한/미존재/중복/용량 오류를 확인했습니다. 실제 브라우저 조작과 사용자 서버·DB 적용은 수행하지 않았습니다. 버전·이력 백엔드 검증은 [수집 단계](../backend/stage-04-ingestion-upload.md#이번-구현-검증)에 기록합니다.

## 데이터셋별 이미지 개수 — 2026-11-13

데이터셋 목록의 워크스페이스 다음에 「이미지 개수」 컬럼을 추가했습니다. API의 imageCount를 현지 숫자 형식과 `개` 단위로 표시하며 빈 데이터셋은 `0개`입니다. 기존 컬럼 조절·선택·우클릭 메뉴는 유지합니다. 서버는 현재 접근 가능한 데이터셋의 dataset_image 메타데이터 수를 목록 SQL 안에서 집계하며 별도 저장 컬럼·디스크 스캔·개별 HTTP 요청은 추가하지 않았습니다. 상세 조회도 동일한 집계 필드를 반환합니다. 실제 디스크 파일이나 썸네일 수를 의미하지 않습니다.

검증: 프런트 TypeScript·Vite 빌드 통과. Java 21에서 DatasetListTest의 관련 테스트 1개만 실행하여 데이터셋별 2개·0개, 다른 공간 제외, 썸네일 없는 이미지 포함, 메타데이터 삭제 후 1개 반영을 확인했습니다. 실제 사용자 DB·서버 및 브라우저 조작 검증은 수행하지 않았습니다.

## 이미지 업로드 버튼·모달 — 2026-11-13

사용자 후속 요청으로 이미지 업로드 UI 구현을 재개했습니다. 이미지 관리 페이지에서 데이터셋을 선택하면 「이미지 업로드」 버튼을 사용할 수 있습니다. 모달에 대상 이름·공간·ID와 업로드 권한 안내를 표시하고 여러 파일 선택·끌어놓기·전송 전 선택 제거를 제공합니다. multipart의 file 한 개씩 기존 API로 순차 전송합니다. Content-Type은 브라우저가 boundary와 함께 지정하도록 별도 설정하지 않습니다.

파일별 대기·전송 중·성공·실패·미전송과 실패 사유를 표시합니다. 중복 409는 「이미 존재하는 이미지입니다」, 413은 서버 용량 제한으로 안내하며 401·403은 나머지 전송을 중단합니다. 통신 오류·서버 장애는 등록 결과가 불명확하므로 자동 재시도하지 않고 목록 확인을 안내합니다. 전송 중 닫기·Escape·중복 시작을 막으며 완료 후 성공·실패·미전송 건수를 같은 모달에 표시하고 목록을 재조회합니다. 화면 종료 시 요청은 취소하지만 서버가 이미 저장했을 수 있어 재접속 후 목록 확인이 필요합니다.

서버는 업로드 권한과 운영자/생성자·활성 멤버십을 최종 검사합니다. 현재 API는 canUpload를 제공하지 않아 버튼은 데이터셋 선택 여부로 활성화하며, 정확한 권한별 숨김 처리를 위해 백엔드를 확장하지 않았습니다. 파일당 제한은 서버 application.yaml을 따르며 화면의 10MB 안내는 기본값입니다. 별도 업로드 결과 모달 대신 업로드 모달 내 결과 영역을 사용합니다. 확대 미리보기는 후속입니다.

2026-11-11 메뉴 동작: 데이터셋 제목은 native details/summary로 하위 목록·생성 메뉴를 접고 펼칩니다. 시작 화면에서는 접힘, `/datasets`·`/datasets/...`에서는 초기 펼침입니다. 마우스 클릭과 키보드 토글을 지원하며 별도 상태 저장은 하지 않습니다. 프런트 빌드와 격리 브라우저의 클릭·Enter 토글·업무 경로 초기 펼침 검증을 통과했습니다.

## 현재 구현: 목록·다중 공간 생성 — 2026-11-11

`/datasets`는 가입 승인된 활성 공간의 독립 데이터셋을 이름·설명·귀속 공간·생성·수정일시로 표시합니다. 이름이 같아도 공간별 별도 ID의 데이터셋이므로 각각 한 행입니다. 로딩·빈 상태·권한/서버 오류와 재시도를 제공하며 상세가 없으므로 가짜 상세 링크는 추가하지 않았습니다.

`/datasets/new`는 가입 공간 조회 후 체크박스 드롭다운으로 하나 이상 선택합니다. 선택 개수·공간 이름·동명 구분용 ID를 표시하고 Escape로 닫을 수 있습니다. “선택한 공간마다 독립 데이터셋이 생성됩니다”를 안내하며 공간이 없거나 로딩 중이면 저장을 막습니다. 성공 응답 배열을 받아 이름·생성 건수와 목록 링크를 표시하고 이름·설명을 초기화합니다. 실패 시 입력을 유지하며 취소는 목록으로 이동합니다. 아래 생성 전용·미구현 설명은 이전 단계 이력입니다.

검증: 변경 관련 Node 테스트 3개 통과, TypeScript·Vite 빌드 통과. 빌드 결과를 격리 브라우저에서 API 응답을 모의하여 두 공간 체크 → 독립 생성 응답 배열 → 목록 두 행·각 공간 표시, 빈 상태·오류·재시도, 320/1280px 페이지 넘침 없음을 확인했습니다. 백엔드 연동 계약은 별도 실제 메모리 DB 테스트로 검증했습니다. 사용자 브라우저·실제 DB는 변경하지 않았습니다.

- 상태: 구현 중 — 로그인·목록·다중 공간 생성 구현
- 갱신일: 2026-11-11
- 선행 단계: 기존 React + TypeScript + Vite 골격. 기능별 구현은 2~8단계의 API·업무 규칙 확정에 의존
- 관련 문서: [제품 개요](../../product/project-overview.md), [아키텍처](../../architecture/architecture.md), [API 계약](../../api/api.md), [진척도 현황판](../README.md#개발-진척도-현황판)

## 목표와 사용자 가치

사용자가 이미지 등록부터 데이터셋 탐색, 처리와 결과 확인까지 이어서 작업할 수 있는 웹 화면을 설계합니다. 프런트 설계와 구현 진척은 이 단계에서 관리하고, 업무 규칙과 서버 계약은 해당 기능 단계 및 API 문서를 참조합니다.

이 문서는 설계 초안입니다. 아래 화면과 구성안은 구현 완료 또는 세부 정책의 채택을 뜻하지 않습니다.

## 범위와 제외 범위

- 범위: 화면 구성과 이동 흐름, 화면 상태, API 호출 경계, 인증·권한에 따른 화면 동작, 기능별 구현 순서와 검증 조건.
- 제외 범위: 백엔드 업무 규칙 변경, 신규 API 구현, 사용자 가입·비밀번호 변경 등 제품 범위가 정해지지 않은 기능.
- 신규 라이브러리, 공통 프레임워크, 개발 도구의 도입은 이 문서 작성만으로 승인되지 않습니다. 필요성과 코드 범위를 구체화한 뒤 별도로 결정합니다.

## 현재 구현 상태

사용자 필드는 [ADR-031](../../decisions/ADR-031-user-identity-fields.md)로 전환했습니다. 로그인은 userId, 내부 참조는 userKey, 실제 이름 표시는 username입니다. 세션과 헤더는 서버 응답을 사용하며 이전 세션을 재사용하지 않습니다. 감사 값은 로그인 아이디가 아닌 내부 키입니다.

2026-11-10 생성 저장 연동: `/datasets/new`에서 실제 POST /api/datasets를 호출합니다. 이름 필수·200자와 설명 선택·2000자를 적용하고 요청 중 필드를 잠그며 실패 시 입력을 유지합니다. 성공 시 이름·ID를 표시하고 입력을 초기화합니다. 상세는 아직 없어 자동 이동하지 않고 취소는 시작 화면으로 이동합니다. 아래 초기 화면만 구현한 기록은 저장 연동 이전 이력입니다.

최신 검증: 프런트 자동 테스트 14개와 타입 검사를 포함한 빌드 성공. Edge에서 인증 헤더·본문, 요청 중 입력 잠금·중복 제출 방지, 성공 초기화, 실패 입력 유지, 320·768·1280px 배치를 API 응답 대체로 확인했습니다. 실제 DB 저장은 백엔드 통합 테스트에서 별도로 검증했습니다.

- `frontend/src/App.tsx`가 시작 화면과 백엔드 연결 상태를 표시합니다.
- `frontend/src/api/health.ts`가 `GET /api/health`를 호출합니다.
- React, TypeScript, Vite와 CSS를 사용하며 라우터·외부 상태 관리·UI 라이브러리는 설치되어 있지 않습니다.
- 로그인 화면을 구현했습니다. 유효한 탭 세션이 없으면 로그인 화면을 표시하며 성공 후 현재 주소의 화면으로 전환합니다. 토큰·만료 시각·아이디는 sessionStorage에 보관해 새로고침 시 복원합니다. 헤더에서 아이디를 확인하고 로그아웃할 수 있습니다. [F2 상세](stage-02-authentication.md)를 참고합니다. 데이터셋 생성·저장은 구현했고 목록·상세·이미지 화면은 미구현입니다.

### 데이터셋 생성 화면 구현 — 2026-11-10

- 사용자 지시 범위는 화면·메뉴·입력 폼입니다. 생성 API 호출, 저장 성공 표시, 목록·상세 화면과 입력 검증 정책은 이번에 구현하지 않았습니다. 생성 버튼은 비활성화하고 저장 준비 중임을 안내합니다.
- 데이터셋 대메뉴 아래 생성 링크는 `/datasets/new`로 이동합니다. 기존 로그인 세션을 사용하며 세션 없이 직접 접근하면 로그인 후 같은 주소의 생성 화면을 표시합니다. 일반 링크 기반 이동이므로 새 라우터 의존성은 없습니다.
- 이름·설명은 명시적 상태와 레이블·안내를 갖는 필드로 구현했습니다. 기본 정보 그룹은 내용에 따라 늘어나고 페이지 스크롤을 사용하며 설명 높이도 조절할 수 있습니다. 미정인 필수 여부·길이 제한은 임의로 설정하지 않았습니다.
- 목록 구현 전의 취소는 시작 화면으로 이동합니다. 입력은 페이지 상태이며 이동·새로고침 시 별도 보관하지 않습니다. 목록·상세 구현 후 확정 흐름에 맞춰 취소·성공 이동을 연결합니다.
- 검증: `node --test frontend/test/login.test.cjs` 12개 통과, `npm --prefix frontend run typecheck`와 `npm --prefix frontend run build` 성공. Edge headless에서 메뉴·입력·키보드 Tab·저장 버튼 비활성화·직접 접근·새로고침·취소·뒤로/앞으로·로그아웃 확인. 320·768·1280px와 200% CSS zoom에서 가로 넘침 없이 실행 버튼 접근을 확인했습니다. CSS 확대 검증이며 브라우저 자체 확대 검증과 구분합니다.
- 브라우저 검증은 격리된 테스트 세션과 헬스 응답 대체를 사용했습니다. 실제 로그인 서버·데이터셋 저장·운영 배포를 검증한 결과는 아닙니다.
- 기존 `node --test frontend/test/*.mjs` 프록시 테스트 1개는 fixture의 `FrontendPort` 누락으로 실패했습니다. Vite 설정은 이번에 변경하지 않았고 보완안은 agent 제안에 기록했습니다.

## 선행 조건과 영향

- 로그인은 [2단계](../backend/stage-02-authentication.md)의 기존 토큰 발급 계약을 사용합니다. 사용자 정보·권한 조회 계약은 현재 제공되지 않으므로 이를 전제로 화면을 구현하지 않습니다.
- 데이터셋 화면은 [3단계](../backend/stage-03-datasets.md)의 식별자, 메타데이터, 소유권 및 조회 계약이 필요합니다.
- 업로드는 [4단계](../backend/stage-04-ingestion-upload.md)의 파일 제한·전송·결과 계약이 필요합니다.
- 전처리·레이블링·클러스터링·플러그인 화면은 각각 [5단계](../backend/stage-05-preprocessing.md), [6단계](../backend/stage-06-labeling.md), [7단계](../backend/stage-07-clustering.md), [8단계](../backend/stage-08-plugin-processing.md)의 입력·결과·실패 모델을 따릅니다.
- API가 없는 화면의 흐름은 설계할 수 있지만, 임의의 엔드포인트나 응답 필드를 확정 계약으로 기록하지 않습니다.

| 데이터셋 목록 | 접근 가능한 데이터셋 탐색과 선택 | 목록 필드·조회·접근 범위 |

| 수집·업로드 | 입력 등록, 진행·성공·실패 결과 확인 | 지원 입력·제한·전송 방식 |
| 전처리·레이블링·클러스터링·플러그인 처리 | 기능별 입력, 실행 또는 저장, 결과 검토 | 각 기능의 업무 규칙과 API |

대표 흐름은 `로그인 → 데이터셋 목록 → 데이터셋 상세 → 이미지 확인 또는 기능별 작업 → 결과 확인`입니다. 상세 화면 안에서 작업을 여는 방식과 별도 화면으로 이동하는 방식, URL 구조는 미결정입니다. 프로젝트·조직 단위 탐색은 해당 업무 개념이 확정된 뒤 검토합니다.

### 코드 구성 초안

- `App.tsx`는 최상위 화면 조합을 담당합니다. 화면 이동 방식이 정해지면 해당 연결을 둡니다.
- API 호출 함수와 HTTP 요청·응답 타입은 기존 `src/api/` 경계를 따릅니다. 화면 내부에 URL과 HTTP 처리를 흩어 놓지 않습니다.
- 업무 화면 코드는 실제 기능을 구현할 때 기능별로 묶습니다. 구체적인 디렉터리와 공통 컴포넌트 추출은 사용처가 생길 때 정하고 빈 구조를 미리 만들지 않습니다.
- 입력값·선택 항목·표시 상태는 해당 화면에 가깝게 관리합니다. 여러 화면에서 실제로 공유해야 하는 상태가 확인되면 소유 위치를 결정합니다.
- 서버 데이터와 화면 임시 입력을 구분합니다. 저장 성공 전에는 서버에 반영된 결과로 표시하지 않습니다.

### 화면 상태와 상호작용

- 조회 화면은 로딩·성공·빈 결과·실패를 구분합니다. 빈 결과에서 사용자가 다음에 할 수 있는 작업은 해당 권한과 기능 범위에 맞게 정합니다.
- 제출 중에는 동일 작업의 중복 제출을 막고, 성공·실패를 화면에 표시합니다. 생성·업로드·작업 실행 요청을 자동 재전송하는 정책은 두지 않고 계약이 정해지면 검토합니다.
- 선택 데이터가 바뀌는 조회는 늦게 도착한 이전 응답이 현재 화면을 덮어쓰지 않도록 구현합니다.
- 장시간 작업은 서버가 제공하는 상태를 표시합니다. 조회 주기, 완료 판정, 취소·재시도 가능 여부는 작업 API 확정 후 결정합니다.
- 입력에는 명시적인 레이블을 제공하고 키보드로 조작할 수 있게 합니다. 색상만으로 상태를 구분하지 않으며 오류와 진행 상태를 텍스트로 전달합니다.
- 주요 작업을 수행할 화면 크기와 이미지 작업 영역의 배치는 실제 사용 환경을 확인한 뒤 결정합니다.

## 데이터·API·권한·오류 처리

### 현재 사용할 수 있는 계약

| API | 용도 | 프런트 상태 |

| `GET /api/health` | 백엔드 연결 확인 | 구현됨 |
| `POST /api/auth/token` | 아이디·비밀번호로 access token 발급 | 로그인 화면·호출 구현 |

API 요청은 기존 상대 경로 `/api`를 기준으로 합니다. 로컬 포트와 빌드 동작은 `bin/local.settings.ps1`에서 관리하며 프런트 설계를 이유로 실행 설정을 중복 추가하지 않습니다.

### 인증과 권한 초안

- 보호된 API에는 `Authorization: Bearer <JWT>`를 전달합니다. 공개 API에는 불필요한 토큰을 보내지 않습니다.
- 현재 refresh token은 없습니다. 만료된 인증으로 요청이 거부되면 재로그인으로 이어지는 흐름을 설계합니다. 토큰은 sessionStorage에서 만료 시각과 함께 복원합니다. 로그아웃·만료 시 제거하며 서버 JWT 자체를 폐기하는 API는 없습니다.
- 비밀번호는 로그인 요청에만 사용하고 로그나 영속 저장소에 남기지 않습니다.
- 프런트의 메뉴·버튼 표시 여부는 사용자 안내를 위한 것이며 최종 접근 권한은 서버가 판정합니다. 권한 조회 API가 없는 현재 상태에서 토큰에 권한 정보가 있다고 가정하지 않습니다.

### 오류 표시 초안

- 로그인 실패는 계정 존재 여부를 구분하지 않는 안내를 제공합니다.
- 보호된 요청의 401은 인증 해제·재로그인 흐름, 403은 접근 불가 안내로 구분합니다. 작성 중 입력의 보존 범위와 복귀 위치는 미결정입니다.
- 네트워크 오류와 서버 오류는 작업 실패를 알리고 사용자가 다음 행동을 선택할 수 있게 합니다. 서버 내부 예외나 토큰을 화면에 그대로 표시하지 않습니다.
- 현재 오류 응답 형식은 API별로 다를 수 있으므로 단일 오류 JSON 형태를 가정하지 않습니다. 구체적인 필드 검증 오류 매핑은 해당 API 계약과 함께 정합니다.
- 이미지 URL 제공·인증 방식과 접근 불가 이미지의 표시 정책은 미결정입니다.

## 데이터셋 상세 모달 — 2026-11-12

목록 이름을 버튼으로 표시하고 마우스 오버 시 포인터·밑줄을 제공합니다. 클릭하면 상세 API를 새로 조회해 메타데이터 모달을 엽니다. 선택 체크박스와 동작을 분리하며 로딩·접근 거부·재시도, 닫기·Escape와 요청 취소를 지원합니다. 서버가 상세 권한과 ACTIVE 공간의 ACTIVE 멤버십을 모두 확인합니다. 이미지 영역은 후속입니다. 계약은 [API](../../api/api.md#데이터셋-상세)를 따릅니다.

프런트 빌드·Node 테스트 통과. Chromium에서 API 응답을 대체하여 포인터, 최신 상세 조회·로딩, 체크박스 미변경, Escape·초점 복원, 403·재시도, 모바일 크기와 닫기를 확인했습니다. 백엔드 권한·멤버십은 별도 선별 테스트로 검증했습니다.

## 데이터셋 관리와 파일 탭 — 2026-11-13

폴더 업로드(ADR-046): 두 탭의 일반·수정 업로드 모달에 폴더 선택을 제공합니다. 선택 폴더와 하위 파일을 파일별 순차 업로드하고 webkitRelativePath를 전달합니다. 선택한 폴더부터의 경로를 업로드 상태·실패 목록·목록 원본명·설명 편집 대상에서 표시합니다. 다른 하위 폴더의 동명 파일은 별개이며 같은 전체 경로만 중복·교체합니다. 빈 폴더는 저장하지 않습니다. 폴더 업로드는 폴더 선택 버튼과 폴더 드래그 앤 드롭 모두 지원합니다. 드롭한 폴더는 하위 폴더와 여러 번에 나누어 반환되는 항목을 끝까지 읽고 선택한 폴더부터의 경로를 보존합니다. 파일·폴더 선택은 별도 버튼으로만 실행하며, 드롭 영역 자체에는 클릭 동작을 두지 않습니다. 브라우저 기본 파일 입력은 숨겨 기본 선택 문구가 표시되지 않게 합니다. 읽는 동안 중복 드롭·선택·업로드 시작을 막고 상태를 표시하며 읽기 실패는 안내합니다. 탭별 허용 형식과 썸네일 정책은 유지합니다.

- 종류: 구현 기준 / 승인·구현: 완료.
- 이미지 관리 메뉴·목록 우클릭·상세 모달 진입 명칭을 데이터셋 관리로 통일했습니다. 현재 경로는 /datasets/manage?tab=images|files&datasetId=...이며 기존 /datasets/images도 같은 페이지를 엽니다.
- 상단 이미지 파일·데이터 파일 탭은 같은 데이터셋 선택을 가능한 경우 유지합니다. 각 탭은 자기 read 권한으로 선택 목록을 조회합니다. 탭/데이터셋 변경 시 저장 전 설명·선택은 초기화됩니다.
- 공통 그리드의 가변 너비·남은 높이 제한·표 하단 가로 스크롤·내부 컬럼 드래그 기준을 유지합니다. 탭 전환 시 기본 컬럼 폭을 적용합니다.
- 이미지 탭은 썸네일·원본 상세와 기존 기능을 유지합니다. 데이터 파일 탭은 썸네일 없이 원본명·버전·파일 확장자·용량·등록/수정 정보를 표시하고 다운로드 버튼을 제공합니다. 확장자 표시는 내용 형식 검증 결과가 아닙니다.
- 두 탭은 파일별 설명 입력·이름 클릭 펼침, 수정 업로드 경고, 중복 실패 목록, 행 펼침 설명 편집·강조·자동 체크, 미선택 변경 건수 확인 후 일괄 저장, 선택 삭제를 제공합니다. 설명 툴팁은 표시하지 않습니다.
- API 및 권한은 [현재 계약](../../api/api.md#데이터-파일-api--2026-11-13)을 따릅니다. 브라우저 실제 조작 검증은 수행하지 않았습니다.

후속 변경(ADR-044): 데이터 파일 업로드 안내를 이미지 포함 모든 형식의 원본 바이너리 저장으로 수정했습니다. 썸네일은 생성·관리하지 않으며 이미지 전용 업로드 안내 오류를 제거했습니다.


폴더 드롭·선택 UI 검증: 프런트 빌드와 선별 테스트 3개 통과. 하위 폴더·여러 배치 읽기·혼합 파일 드롭·경로/내용 보존·빈 폴더·읽기 실패·두 API 경로 전송과 숨긴 입력/별도 버튼 출력을 확인했습니다. 브라우저 실제 드래그 조작은 검증하지 않았습니다. 프런트만 변경하여 백엔드는 재시작하지 않았습니다.
