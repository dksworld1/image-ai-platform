# 프런트 단계: 화면과 사용자 흐름 설계

- 상태: 설계 중
- 갱신일: 2026-11-08
- 선행 단계: 기존 React + TypeScript + Vite 골격. 기능별 구현은 2~8단계의 API·업무 규칙 확정에 의존
- 관련 문서: [제품 개요](../../product/project-overview.md), [아키텍처](../../architecture/architecture.md), [API 계약](../../api/api.md), [진척도 현황판](../README.md)

## 목표와 사용자 가치

사용자가 이미지 등록부터 데이터셋 탐색, 처리와 결과 확인까지 이어서 작업할 수 있는 웹 화면을 설계합니다. 프런트 설계와 구현 진척은 이 단계에서 관리하고, 업무 규칙과 서버 계약은 해당 기능 단계 및 API 문서를 참조합니다.

이 문서는 설계 초안입니다. 아래 화면과 구성안은 구현 완료 또는 세부 정책의 채택을 뜻하지 않습니다.

## 범위와 제외 범위

- 범위: 화면 구성과 이동 흐름, 화면 상태, API 호출 경계, 인증·권한에 따른 화면 동작, 기능별 구현 순서와 검증 조건.
- 제외 범위: 백엔드 업무 규칙 변경, 신규 API 구현, 사용자 가입·비밀번호 변경 등 제품 범위가 정해지지 않은 기능.
- 신규 라이브러리, 공통 프레임워크, 개발 도구의 도입은 이 문서 작성만으로 승인되지 않습니다. 필요성과 코드 범위를 구체화한 뒤 별도로 결정합니다.

## 현재 구현 상태

- `frontend/src/App.tsx`가 시작 화면과 백엔드 연결 상태를 표시합니다.
- `frontend/src/api/health.ts`가 `GET /api/health`를 호출합니다.
- React, TypeScript, Vite와 CSS를 사용하며 라우터·외부 상태 관리·UI 라이브러리는 설치되어 있지 않습니다.
- 로그인 화면을 구현했습니다. 유효한 탭 세션이 없으면 로그인 화면을 표시하며 성공 후 시작 화면으로 전환합니다. 토큰·만료 시각·아이디는 sessionStorage에 보관해 새로고침 시 복원합니다. 헤더에서 아이디를 확인하고 로그아웃할 수 있습니다. [F2 상세](stage-02-authentication.md)를 참고합니다. 데이터셋 및 이미지 업무 화면은 미구현입니다.

## 선행 조건과 영향

- 로그인은 [2단계](../backend/stage-02-authentication.md)의 기존 토큰 발급 계약을 사용합니다. 사용자 정보·권한 조회 계약은 현재 제공되지 않으므로 이를 전제로 화면을 구현하지 않습니다.
- 데이터셋 화면은 [3단계](../backend/stage-03-datasets.md)의 식별자, 메타데이터, 소유권 및 조회 계약이 필요합니다.
- 업로드는 [4단계](../backend/stage-04-ingestion-upload.md)의 파일 제한·전송·결과 계약이 필요합니다.
- 전처리·레이블링·클러스터링·플러그인 화면은 각각 [5단계](../backend/stage-05-preprocessing.md), [6단계](../backend/stage-06-labeling.md), [7단계](../backend/stage-07-clustering.md), [8단계](../backend/stage-08-plugin-processing.md)의 입력·결과·실패 모델을 따릅니다.
- API가 없는 화면의 흐름은 설계할 수 있지만, 임의의 엔드포인트나 응답 필드를 확정 계약으로 기록하지 않습니다.

## 핵심 개념과 원리

### 화면 구성 초안

| 화면 | 사용자의 주요 작업 | 설계 의존성 |
|---|---|---|
| 로그인 | 아이디·비밀번호 입력, 로그인 결과 확인 | 토큰 발급·만료 처리 |
| 데이터셋 목록 | 접근 가능한 데이터셋 탐색과 선택 | 목록 필드·조회·접근 범위 |
| 데이터셋 상세 | 이미지 목록과 메타데이터 확인 | 페이지 조회·정렬·필터 계약 |
| 이미지 상세 | 이미지와 메타데이터·관련 결과 확인 | 이미지 제공 방식·원본과 파생 결과 관계 |
| 수집·업로드 | 입력 등록, 진행·성공·실패 결과 확인 | 지원 입력·제한·전송 방식 |
| 전처리·레이블링·클러스터링·플러그인 처리 | 기능별 입력, 실행 또는 저장, 결과 검토 | 각 기능의 업무 규칙과 API |

대표 흐름은 `로그인 → 데이터셋 목록 → 데이터셋 상세 → 이미지 확인 또는 기능별 작업 → 결과 확인`입니다. 상세 화면 안에서 작업을 여는 방식과 별도 화면으로 이동하는 방식, URL 구조는 미결정입니다. 프로젝트·조직 단위 탐색은 해당 업무 개념이 확정된 뒤 검토합니다.

### 코드 구성 초안

- `App.tsx`는 최상위 화면 조합을 담당합니다. 화면 이동 방식이 정해지면 해당 연결을 둡니다.
- API 호출 함수와 HTTP 요청·응답 타입은 기존 `src/api/` 경계를 따릅니다. 화면 내부에 URL과 HTTP 처리를 흩어 놓지 않습니다.
- 업무 화면 코드는 실제 기능을 구현할 때 기능별로 묶습니다. 구체적인 디렉터리와 공통 컴포넌트 추출은 사용처가 생길 때 정하고 빈 구조를 미리 만들지 않습니다.
- 입력값·선택 항목·표시 상태는 해당 화면에 가깝게 관리합니다. 여러 화면에서 실제로 공유해야 하는 상태가 확인되면 소유 위치를 결정합니다.
- 서버 데이터와 화면 임시 입력을 구분합니다. 저장 성공 전에는 서버에 반영된 결과로 표시하지 않습니다.

### 화면 상태와 상호작용

- 조회 화면은 로딩·성공·빈 결과·실패를 구분합니다. 빈 결과에서 사용자가 다음에 할 수 있는 작업은 해당 권한과 기능 범위에 맞게 정합니다.
- 제출 중에는 동일 작업의 중복 제출을 막고, 성공·실패를 화면에 표시합니다. 생성·업로드·작업 실행 요청을 자동 재전송하는 정책은 두지 않고 계약이 정해지면 검토합니다.
- 선택 데이터가 바뀌는 조회는 늦게 도착한 이전 응답이 현재 화면을 덮어쓰지 않도록 구현합니다.
- 장시간 작업은 서버가 제공하는 상태를 표시합니다. 조회 주기, 완료 판정, 취소·재시도 가능 여부는 작업 API 확정 후 결정합니다.
- 입력에는 명시적인 레이블을 제공하고 키보드로 조작할 수 있게 합니다. 색상만으로 상태를 구분하지 않으며 오류와 진행 상태를 텍스트로 전달합니다.
- 주요 작업을 수행할 화면 크기와 이미지 작업 영역의 배치는 실제 사용 환경을 확인한 뒤 결정합니다.

## 데이터·API·권한·오류 처리

### 현재 사용할 수 있는 계약

| API | 용도 | 프런트 상태 |
|---|---|---|
| `GET /api/health` | 백엔드 연결 확인 | 구현됨 |
| `POST /api/auth/token` | 아이디·비밀번호로 access token 발급 | 로그인 화면·호출 구현 |

API 요청은 기존 상대 경로 `/api`를 기준으로 합니다. 로컬 포트와 빌드 동작은 `bin/local.settings.ps1`에서 관리하며 프런트 설계를 이유로 실행 설정을 중복 추가하지 않습니다.

### 인증과 권한 초안

- 보호된 API에는 `Authorization: Bearer <JWT>`를 전달합니다. 공개 API에는 불필요한 토큰을 보내지 않습니다.
- 현재 refresh token은 없습니다. 만료된 인증으로 요청이 거부되면 재로그인으로 이어지는 흐름을 설계합니다. 토큰은 sessionStorage에서 만료 시각과 함께 복원합니다. 로그아웃·만료 시 제거하며 서버 JWT 자체를 폐기하는 API는 없습니다.
- 비밀번호는 로그인 요청에만 사용하고 로그나 영속 저장소에 남기지 않습니다.
- 프런트의 메뉴·버튼 표시 여부는 사용자 안내를 위한 것이며 최종 접근 권한은 서버가 판정합니다. 권한 조회 API가 없는 현재 상태에서 토큰에 권한 정보가 있다고 가정하지 않습니다.

### 오류 표시 초안

- 로그인 실패는 계정 존재 여부를 구분하지 않는 안내를 제공합니다.
- 보호된 요청의 401은 인증 해제·재로그인 흐름, 403은 접근 불가 안내로 구분합니다. 작성 중 입력의 보존 범위와 복귀 위치는 미결정입니다.
- 네트워크 오류와 서버 오류는 작업 실패를 알리고 사용자가 다음 행동을 선택할 수 있게 합니다. 서버 내부 예외나 토큰을 화면에 그대로 표시하지 않습니다.
- 현재 오류 응답 형식은 API별로 다를 수 있으므로 단일 오류 JSON 형태를 가정하지 않습니다. 구체적인 필드 검증 오류 매핑은 해당 API 계약과 함께 정합니다.
- 이미지 URL 제공·인증 방식과 접근 불가 이미지의 표시 정책은 미결정입니다.

## 미결정 질문과 후속 조치

1. [프런트 구현 단계 F1~F5](README.md#구현-단계)에 따라 첫 구현 범위와 대표 사용자 작업을 구체화합니다. 화면 기반 구성 → 인증 → 데이터셋·이미지 탐색 → 수집·업로드 → 이미지 작업·결과 검토 순서로 나눕니다.
2. 화면 이동·URL 구조, 로그인 유지 요구와 토큰 저장 정책을 정합니다.
3. 주요 화면의 배치, 공통 탐색 영역, 대상 화면 크기와 시각 스타일을 구체화합니다.
4. 각 업무 단계에서 조회·입력·작업 상태 계약이 확정되면 해당 화면 설계와 완료 조건을 보완합니다.
5. 필요한 라이브러리가 확인되면 목적·추가 범위·필요성을 제시하고 도입 여부를 결정합니다.

## 완료 조건과 검증 결과

### 설계 완료 조건

- 첫 구현 화면 범위와 이동 흐름이 확정되어 있습니다.
- 인증 유지·만료·로그아웃, 권한 부족 및 오류 표시 정책이 정해져 있습니다.
- 첫 구현 범위의 API·타입·권한 계약과 화면 상태가 대응됩니다.
- 필요한 의존성과 중요한 구조 결정이 승인되고 해당 ADR과 연결되어 있습니다.

### 구현 완료 조건

- 확정한 화면에서 정상 흐름과 로딩·빈 결과·실패 흐름을 확인합니다.
- 인증 성공·실패·만료, 보호된 요청의 401·403 동작을 검증합니다.
- 변경 기능에 맞는 자동 검증을 추가하거나 갱신하고 실제 실행 결과를 기록합니다. 테스트 도구의 신규 도입이 필요하면 먼저 승인받습니다.
- `frontend/`에서 `npm run typecheck`, `npm run build`가 성공합니다. 이 명령만으로 화면 기능 검증을 대체하지 않습니다.
- 키보드 조작, 입력 레이블, 상태 안내와 합의한 화면 크기의 배치를 확인합니다.
