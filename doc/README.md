## 카테고리 정의와 배치 기준

이 절은 새 문서의 저장 위치를 정하는 기준입니다. 제목에 붙은 “설계”, “정의”, “계획”보다 문서가 답하는 핵심 질문과 주된 사용 목적을 우선합니다. 상태는 별도로 표시하며 초안이라는 이유만으로 모두 `plans/`에 넣지 않습니다.

| 위치 | 성격·핵심 질문 | 포함할 내용 | 배치 경계 |
|---|---|---|---|

## 신규 문서 작성 순서

1. 같은 주제의 기준 문서가 있는지 먼저 확인합니다. 목적과 독자가 같으면 기존 문서를 갱신하고, 별도 검토·갱신 단위가 필요할 때 새 파일을 만듭니다.
2. 위 표에서 주된 목적에 맞는 카테고리를 선택합니다. 같은 업무의 계획·설계 제안·진척은 함께 작성할 수 있습니다. 요구사항·화면·API·DB·운영처럼 기준이 다른 내용은 각 소유 문서에 두고 링크합니다.
3. 경로는 기존 구조를 우선합니다. 파일명은 내용을 설명하는 영문 소문자·하이픈 형태를 사용하고, ADR-NNN과 stage-NN 등 기존 식별 규칙은 유지합니다. 화면 자산은 기능 폴더 안에서 기존 버전명 규칙을 따릅니다.
4. 종류·상태·작성일 또는 갱신일·관련 기준 문서를 식별할 수 있게 기록합니다. 승인 상태와 구현 상태가 다르면 각각 명시하고, 미정 항목은 별도로 남깁니다. ADR·단계·설계 제안은 해당 서식을 사용합니다.
5. 새 문서는 가까운 업무·카테고리 색인에 연결합니다. 별도 색인이 없으면 상위 색인에 연결하며, 주요 진입 문서는 이 문서에도 추가합니다. 업무상 이유 없이 빈 폴더나 새 최상위 카테고리를 미리 만들지 않습니다.
6. 이동·통합 시 본문·승인 상태·기준일·검증 근거·원본 자산을 보존하고 모든 참조와 상대 링크·앵커를 갱신합니다. 상태 전환 시 아래 기준으로 기준 문서도 함께 갱신합니다.

## 여러 성격이 섞인 경우와 상태 전환

한 사실의 상세는 한 기준 문서에서 관리합니다. 다른 문서는 목적에 필요한 요약과 링크만 둡니다. 예를 들어 “데이터셋 생성”은 다음처럼 배치합니다.

| 작성할 내용 | 위치 |
|---|---|
| 사용자가 데이터셋을 만드는 목적·입력 규칙·사용자 시나리오 | product의 기능 정의 또는 해당 업무 요구 문서 |
| 생성 기능의 작업 ID·선행 조건·완료 기준·미정 대안 | plans의 데이터셋 작업계획서 |
| 생성 페이지의 이름·설명 입력과 저장·취소·오류 배치 | storyboards/dataset-management |
| 생성 API의 경로·요청 필드·성공·실패 응답 | api의 해당 업무 계약 |
| 데이터셋 테이블·공통 컬럼·소유자 관계 | db-schema의 공통 규칙과 해당 업무 테이블 정의 |
| 소유·공유 구조 등 중요한 대안의 채택 근거 | decisions의 새 ADR |
| 스키마를 환경에 적용하는 순서와 실제 적용 결과 | operations의 마이그레이션·배포 문서 |

- 제안 승인: 원래 제안은 plans에서 상태·결정·결과 링크를 갱신합니다. 중요한 결정은 ADR에 기록하고 영향받는 제품·화면·기술 계약을 갱신합니다. 승인만으로 구현 완료로 표시하지 않습니다.
- 구현 완료: 실제 코드·검증을 확인한 뒤 현재 아키텍처·API·DB 정의와 해당 계획·단계의 완료 근거를 함께 갱신합니다. 운영 DB 적용 여부는 별도로 기록합니다.
- 보류·거부: 원래 문서에 상태와 이유를 남깁니다. 기능 자체가 폐기되지 않았다면 archive로 이동하지 않습니다.
- 기능 폐기: 현재 계약에서 제거 사실과 이력 링크를 표시하고 폐기 기능 문서·자산을 archive/<기능>로 모읍니다. ADR과 실제 운영 기록은 원래 위치에 유지합니다.

설계 논의가 확정 계약과 섞여 있는 기존 문서를 갱신할 때는 해당 부분의 상태를 먼저 확인합니다. 이번 분류 정의만으로 기존 초안·제안·구현 상태를 변경하지 않습니다.

2026-11-10: 루트 안내·작업 지침과 `doc/`의 Markdown 75개를 점검했습니다. 단계 문서를 `plans/front/`·`plans/backend/`로 통합하고 로드맵·현황판을 `plans/README.md`에 합쳤습니다. 폐기된 UI의 API·테이블·스토리보드는 `archive/ui/`로 모았습니다. 기존 정책·검증 이력과 원본 이미지는 보존했습니다.

## 기록 원칙

1. 기능 구현의 목표, 범위, 선행 조건, 핵심 개념과 완료 조건을 해당 단계 문서에 기록합니다.
2. 논의 중이거나 미확정인 내용은 `미결정`으로 표시하고, 채택한 결정은 근거와 영향까지 기록합니다.
3. 여러 단계에 영향을 주는 기술·구조 결정은 `decisions/`에 새 번호의 ADR로 남기고 관련 단계 문서에서 연결합니다.
4. 구현 상태는 실제 코드와 검증 결과를 확인한 뒤 갱신합니다. 실행하지 않은 검증을 완료로 기록하지 않습니다.
5. 아키텍처·API·제품 방향이 달라지면 해당 기준 문서와 영향을 받는 단계 문서를 함께 갱신합니다.
   개발 계획·설계 제안·단계별 기록과 진척은 `plans/`에서 통합 관리하며, 문서의 종류와 승인·구현 상태로 구분합니다.
6. 권한 모듈의 정책·구조 설계와 보완 논의는 현재 [권한 시스템 설계 제안](plans/authorization-design-proposal.md)에서 관리하고 추후 별도 설계 문서로 이관합니다. 스키마 정의는 [인증·권한 테이블 정의서](db-schema/tables/auth/README.md)에서 먼저 관리하며 제안서는 이를 링크합니다. 그 밖의 관련 문서는 제안서 링크와 현재 구현 상태·진행 상황을 기록하고 상세 설계는 중복 작성하지 않습니다.

문서는 한국어로 작성하고 코드, 명령어, 경로, API 식별자와 고유 기술명은 원문을 유지합니다.

단계 문서를 새로 만들 때는 [단계 기록 서식](templates/stage-record.md)을 사용합니다.
