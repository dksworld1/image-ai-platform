# 공고 적합도 및 프로젝트 어필 전략

기준일: 2026-11-02  
대상 공고: [전사 통합 Image 솔루션 제공 플랫폼 Application 개발·운영 PL](https://www.skcareers.com/Recruit/Detail/R261970)  
분석 근거: 공고 페이지와 2026-11-02 기준 저장소 코드·문서

## 1. 공고 요약

공고의 직무는 SK 주력 관계사 제조 현장의 AI·Data 전환을 지원하는 Application 구축·운영이며, 제목은 전사 통합 Image 솔루션 제공 플랫폼의 개발·운영 PL 영입입니다. 주요 기술은 Java, Spring Boot, React, Oracle, Kafka입니다. 공고는 관계형 DB 및 인터페이스 설계, 성능 개선, 장애 원인 분석과 기술 지원, 다양한 이해관계자와의 커뮤니케이션을 요구합니다. 우대 항목에는 대규모 SI/SM, MSA·DevOps와 CI/CD, Vision 프로젝트, DB/WAS/Application 튜닝, 클라우드·오픈소스 적용, PM/PL 또는 개발 리딩과 서비스 고도화 경험이 포함됩니다.

공고에는 관련 분야 경력 3년 이상 요건도 있습니다. 이는 프로젝트 결과물로 대체할 수 있는 항목이 아니므로 지원 자격과 실제 경력은 별도로 확인해야 합니다.

## 2. 현재 프로젝트와의 연결

저장소의 제품 방향은 이미지 데이터 수집, 데이터셋 관리, 전처리, 레이블링, 클러스터링, 플러그인 기반 처리 플랫폼입니다. 따라서 공고의 Image 솔루션과 제품 주제의 연결성이 높습니다. 현재 기술 기반도 Java 21/Spring Boot, React/TypeScript와 관계형 DB 접근 구성을 포함합니다. 다만 공고의 Oracle 및 Kafka는 현재 저장소에서 구현 근거가 확인되지 않습니다.

현재 구현은 제품 기능 초기 단계입니다. 문서에 계획된 기능을 이미 제공 중인 것처럼 표현하면 안 됩니다.

## 3. 저장소에서 확인되는 강점

| 강점 | 확인 근거 | 지원 자료에서의 활용 |
|---|---|---|
| 직무와 직접 연결되는 이미지 플랫폼 문제를 선택함 | `doc/product/project-overview.md`에서 이미지 수집부터 가공·레이블링·탐색까지의 제품 방향 정의 | 공고의 통합 Image 솔루션과 문제 영역이 맞닿아 있음을 설명 |
| Java/Spring Boot와 React 기반을 실제 저장소에 구성함 | `backend/`, `frontend/`, `doc/architecture/architecture.md` | 공고의 주요 애플리케이션 기술과 연결. 숙련도나 실무 수준은 별도 입증 필요 |
| 관계형 DB 접근 경계를 명시적으로 설계함 | 다중 데이터소스, MyBatis, DAO 및 qualifier 설계를 다룬 ADR-002·005·006 및 1단계 문서 | DB/interface 설계를 고민한 사례로 활용. Oracle 실무 경험의 증거로 확대 해석하지 않음 |
| 구조·운영 고려사항을 문서로 축적함 | 프로파일별 설정과 로그, 데이터소스 분리, 스키마 초기화 조건, 단계별 완료 기준 등 | 설계 의사결정과 기술적 근거를 설명할 수 있는 재료 |
| 요구사항과 구현 상태를 분리하는 습관 | 제품 개요와 로드맵에 예정 기능과 실제 구현을 구분한다고 명시 | 과장 없이 범위·미결정 사항을 관리하는 태도를 보여줌 |

이는 저장소 산출물 기반 평가입니다. 협업, 커뮤니케이션, 책임감, 학습 속도 등 개인 역량은 이 저장소만으로 확인되지 않습니다.

## 4. 현재 드러나는 약점과 증거 공백

| 공고 관점 | 지금 확인되는 공백 | 프로젝트에서 보완할 수 있는 증거 |
|---|---|---|
| 운영 및 장애 분석 | 헬스체크 외 업무 API, 장애 시나리오/대응 기록, 관측 지표가 제한적 | 오류 경계, 로그·메트릭, 장애 재현과 원인 분석 기록, 복구 절차를 실제 구현·검증 |
| DB 설계와 성능 튜닝 | 데이터 기반은 있으나 이미지 업무 스키마, 대표 쿼리, 측정 전후 수치가 아직 없음 | 데이터 모델 근거, 인덱스 선택, explain/부하 측정 등 재현 가능한 튜닝 사례 |
| 공고 스택 정합성 | Oracle과 Kafka 적용 근거 없음 | 요구가 확인될 때 실제 필요성을 검토하고, 선택 또는 미선택 근거를 ADR로 설명. 포트폴리오 목적으로만 무리하게 추가하지 않음 |
| PL·리딩 및 이해관계자 조율 | 개인 프로젝트 저장소만으로 팀 리딩·조율 성과를 증명할 수 없음 | 실제 사용자/가상 이해관계자 요구, 범위 조정, 결정 로그와 회고를 기록하되 협업 경험으로 허위 표기하지 않음 |
| 배포·DevOps 및 서비스 고도화 | 로컬 실행과 독립 실행 중심이며 CI/CD·운영 배포 증거는 아직 확인되지 않음 | 자동 빌드·검증, 배포 절차, 설정·비밀 관리와 운영 가이드를 추가하고 실제 동작을 확인 |
| Vision/AI 실무 | 이미지 플랫폼 지향은 있으나 Vision 모델 처리 성과는 아직 확인되지 않음 | 데이터 흐름과 모델/처리 플러그인 인터페이스를 구현할 경우 품질·성능·재현성까지 기록 |
| 지원 자격 | 공고의 3년 이상 경력 여부는 저장소로 알 수 없음 | 지원서 작성 전 본인 경력 사실과 공고 요건을 대조 |

## 5. 다음 작업에서 우선 추천할 어필 요소

1. **통합 이미지 처리 흐름을 끝까지 구현**: 업로드 → 데이터셋/메타데이터 → 처리 작업 → 상태/실패 확인의 핵심 시나리오를 좁게 정하고 실제 동작으로 연결합니다.
2. **DB/API 계약의 설계 근거를 남김**: 이미지와 처리 작업의 식별자, 상태, 이력, 중복·재시도 규칙을 정하고 스키마와 API 문서에 반영합니다.
3. **운영 가능한 실패 처리**: 입력 오류, 저장 실패, 장시간 작업, 재시도와 중복 요청 시 동작을 명시하고 로그 및 검증 결과를 남깁니다.
4. **측정 가능한 성능 사례**: 대표 데이터와 실행 조건을 고정하고 기준선·개선 후 결과를 비교합니다. 수치가 없으면 개선 효과를 주장하지 않습니다.
5. **배포·자동 검증 경로**: 저장소 변경 시 빌드와 필요한 검증이 반복 가능하도록 구성하고, 사용한 명령과 실제 결과를 기록합니다.
6. **PL 관점의 의사결정 기록**: 목표, 범위, 의존성, 위험, 선택지, 결정 근거와 후속 조치를 ADR·단계 문서에 연결합니다. 개인 작업을 팀 리딩으로 표현하지 않습니다.

우선순위는 실제 제품 방향과 사용자 요구를 기준으로 조정하며, Oracle/Kafka/MSA 등은 공고 키워드만을 이유로 도입하지 않습니다.

## 6. 현시점에서 쓸 수 있는 프로젝트 소개 초안

> Java/Spring Boot와 React 기반으로 이미지 데이터 수집·관리·처리 플랫폼을 설계하고 구현 중입니다. 저장소에는 백엔드·프런트엔드 실행 기반과 관계형 데이터 접근 구조, 단계별 설계 및 기술 의사결정 기록을 구축했습니다. 현재 제품 기능은 초기 단계이며, 이후 이미지 처리 흐름과 운영·성능 검증 사례를 실제 구현 결과에 맞춰 확장하고 있습니다.

이 문구는 저장소 상태를 반영한 초안입니다. 향후 기능 및 검증이 완료될 때마다 구체적인 역할·기술·측정 결과를 근거와 함께 갱신해야 합니다.

## 7. 다음에 확인할 개인 정보

프로젝트 분석만으로 판단할 수 없는 지원 적합도 항목입니다. 사용자가 제공하면 사실 검증 가능한 지원 자료로 연결합니다.

- 총 경력 및 관련 직무 경력 연수, 각 역할과 기간
- 실제 운영 장애 분석·성능 개선·기술 지원 사례와 결과
- Oracle, Kafka, 제조·Vision 시스템의 실무 사용 여부
- SI/SM 규모, 협업한 이해관계자, 본인이 맡은 조율·리딩 범위
- CI/CD, 클라우드, 배포 및 서비스 고도화 경험
- 성과를 뒷받침할 수 있는 측정치나 산출물
