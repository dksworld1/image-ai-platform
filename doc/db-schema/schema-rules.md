# 프로젝트 공통 스키마 생성 규칙

상태: 확정  
확정일: 2026-11-10  
관련 결정: [ADR-028](../decisions/ADR-028-common-audit-columns.md), [ADR-031](../decisions/ADR-031-user-identity-fields.md)

## 적용 범위

모든 프로젝트 소유 테이블에 아래 4개 컬럼을 둡니다. 업무·연결·기반·테스트용 테이블에 동일하게 적용합니다. Flyway가 관리하는 `flyway_schema_history` 등 외부 도구 소유 테이블은 수정하지 않습니다. V4에서 삭제한 UI 테이블과 과거 마이그레이션 파일은 이력으로 보존합니다.

## 공통 컬럼

| 컬럼 | 의미 | SQL 형식 | NULL | INSERT 기본값 | Java 형식 |
|---|---|---|---|---|---|
| `created_at` | 생성일 | `TIMESTAMP WITH TIME ZONE` | 불가 | `CURRENT_TIMESTAMP` | `OffsetDateTime` |
| `updated_at` | 수정일 | `TIMESTAMP WITH TIME ZONE` | 불가 | `CURRENT_TIMESTAMP` | `OffsetDateTime` |
| `created_by` | 생성자 | `VARCHAR(100)` | 불가 | `'0'` | `String` |
| `updated_by` | 수정자 | `VARCHAR(100)` | 불가 | `'0'` | `String` |

시각은 시간대를 포함한 절대 시점으로 다루며 표시 시간대와 구분합니다. `CURRENT_TIMESTAMP`는 DB의 현재 시점을 사용합니다. 생성 시 생성일과 수정일에 같은 시점을, 생성자와 수정자에 같은 작업자를 기록합니다. 수정 시 생성일·생성자는 보존하고 수정일·수정자만 갱신합니다. UPDATE 기본값이나 트리거로 수정 정보를 자동 갱신하지 않으며 해당 SQL에서 명시합니다. 생성 시 기본값은 시스템 INSERT를 지원하기 위한 것으로, 사용자 작업에서 작업자 전달을 생략하는 용도로 사용하지 않습니다.

## 작업자 식별자

- 사용자 작업: 서버가 확인한 로그인 사용자의 내부 `user_key`를 기록합니다. 로그인 아이디 `user_id`나 실명 `username`, 요청 본문의 생성자·수정자를 기록 근거로 사용하지 않습니다.
- 시스템 작업: 내부 키 문자열 `'0'`을 사용합니다. 초기 seed·기반 probe·자동 작업에 적용합니다. auth_user의 CHECK 제약은 이 내부 키의 계정 생성을 거부합니다.
- `'0'`용 로그인 계정은 만들지 않습니다. 화면에서 표시할 때는 “시스템”으로 표현할 수 있습니다.
- 생성자·수정자에는 사용자 FK를 설정하지 않습니다. 사용자 삭제 이후에도 식별자를 보존하며 시스템 작업도 표현합니다.
- `VARCHAR(100)`은 기존 내부 참조값 보존과 새 UUID 키를 수용하는 크기입니다. 시스템 값은 짧은 `'0'`을 사용하며 숫자 사용자 키 체계는 도입하지 않습니다.

## 기존 데이터와 마이그레이션

V7→V8→V9에서 기존 로그인 식별자 값을 변경 없이 user_key로 보존하고 초기 user_id에도 복사합니다. 이미 기록된 작업자 컬럼은 그대로 내부 키를 가리키므로 일괄 치환하지 않습니다. 이관은 과거 감사 시각·작업자를 덮어쓰지 않습니다. 아래 V5 예약값 username 설명은 당시 구조이며 현재 예약 대상은 user_key입니다.

app의 기존 인증·권한 5개 테이블은 V5 DDL에서 컬럼과 기본값을 추가합니다. 기존 행은 추가 시점의 시각과 `'0'`으로 보정됩니다. 이는 과거 실제 생성·수정 이력의 복원이 아닙니다. 기존 `'0'` 계정이 있으면 예약값 제약 적용 전에 운영자가 해당 계정과 연결 데이터를 별도로 정리해야 합니다.

V1~V4는 체크섬을 유지합니다. 신규 DB도 V1~V5를 순서대로 적용해 같은 최종 스키마를 구성합니다. DDL은 `db/migration/`, seed와 그 밖의 데이터 변경 SQL은 `db/seed/`에 둡니다.

legacy catalog/archive의 `foundation_probe`는 자동 마이그레이션 대상이 아닙니다. 기존 테이블용 ALTER SQL을 각각 `db/migration/catalog/`, `db/migration/archive/`에 두며 사전 프로비저닝 절차에서 적용합니다. 신규 생성 구조는 [테이블 정의서](tables/foundation/foundation-probe.md)를 따릅니다. 테스트 fixture는 최종 구조로 생성합니다.

## 백엔드 적용 범위

인증·권한 5개 record에 공통 필드를 직접 선언하고 실제 계정 조회 MyBatis 생성자 매핑에 연결합니다. 권한 코드만 반환하는 조회는 필요한 코드만 계속 반환합니다. 현재 인증·권한 쓰기 API는 없으며 local seed는 생성 정보 보존과 수정 정보 갱신을 수행합니다. foundation probe INSERT는 시스템 작업자와 두 시각을 명시합니다.

공통 상속 모델, 자동 감사 인터셉터, 스키마 기동 검사기는 추가하지 않습니다. 공통 컬럼은 현재 행의 생성·최종 수정 정보이며 삭제 이력이나 모든 변경 내역을 보관하는 감사 로그를 대신하지 않습니다.
