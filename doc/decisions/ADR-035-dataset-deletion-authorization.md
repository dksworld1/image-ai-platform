# ADR-035: 데이터셋 삭제의 기능 권한과 공간 범위

- 상태: 채택 — 삭제 백엔드 구현, UI·이미지 처리 제외
- 날짜: 2026-11-11
- 관련 기록: [ADR-026](ADR-026-service-permission-boundary.md), [ADR-034](ADR-034-independent-dataset-creation.md)

## 맥락

사용자는 UI 설계와 이미지 삭제를 이번 작업에서 제외하고 데이터셋 삭제 로직을 요청했습니다. 공간 운영자는 자기 공간의 데이터셋을 삭제하고, 일반 사용자는 자기가 생성한 데이터셋이면서 그 공간의 멤버인 경우만 삭제할 수 있어야 합니다. 이전 논의의 이미지 생성자 조건은 적용하지 않습니다.

## 대안

- 생성자만 검사: 탈퇴한 사용자가 과거 데이터에 접근할 수 있으므로 불가합니다.
- 전역 관리자 역할만 검사: 다른 공간의 데이터까지 삭제할 수 있으므로 불가합니다.
- 기능 권한·활성 멤버십·공간 상태·운영자/생성자 조건을 결합: 기능 사용 허용과 데이터 범위를 분리할 수 있습니다.

## 결정

서비스 삭제 메서드에 다음 조건을 명시합니다.

```java
@PreAuthorize("@authorizationService.hasPermission('dataset:item:delete') and @datasetService.canDelete(#datasetId)")
```

공통 기능 권한 검사는 활성 계정과 현재 부여 권한을 확인합니다. 대상 범위는 실제 dataset.workspace_id로 결정하고 ACTIVE 공간·해당 공간의 ACTIVE 멤버십을 필수로 요구합니다. 추가로 공간 owner_user_key 일치, 공간 내 ADMIN 역할, dataset.created_by 일치 중 하나를 만족해야 합니다. 모두 내부 user_key를 비교합니다. 생성자나 OWNER라도 활성 멤버십이 없으면 거부합니다. 전역 admin 역할은 공간 접근 우회가 아닙니다.

권한 확인은 서비스 Method Security에서, 대상 범위는 `canDelete`와 실제 조건부 DELETE에서 같은 MyBatis SQL 조각을 사용해 검사합니다. 단순 사전 조회 결과만 믿고 ID로 무조건 삭제하지 않습니다. 실제 DELETE가 1행을 삭제하지 못하면 거부합니다. 이는 문장 실행 시 범위 확인이며 이미 진행 중인 모든 권한 회수 작업을 전역 직렬화하는 별도 장치는 아닙니다.

없는 ID·공간 미귀속·접근 불가·생성자 불일치는 동일한 403으로 처리해 대상 존재를 구분하지 않습니다. 성공은 204입니다. 현재 데이터셋 DB 행만 물리 삭제하며 UI·이미지 DB/파일·삭제 배치·삭제 이력 테이블은 추가하지 않습니다. 공간별 독립 데이터셋에는 영향을 주지 않습니다.

## 결과

후속 사용자 요청으로 목록의 행·전체 선택과 선택 삭제 UI를 추가했습니다. 기존 단건 DELETE를 항목별 호출하며 실패 행은 남깁니다. 본 ADR에서 최초 제외한 이미지·배치는 여전히 구현하지 않았습니다. 화면 흐름은 [프런트 기록](../plans/front/design.md#목록-행-선택삭제--2026-11-11)을 따릅니다.

기존 `dataset:item:delete` 카탈로그를 재사용합니다. local admin 역할에는 반복 local seed에서 삭제 기능 권한을 명시적으로 연결합니다. 일반 사용자에게 자동으로 새 역할을 만들거나 권한을 부여하지 않으며 기존 역할에 삭제 기능 권한이 할당되어야 합니다. 운영 환경에도 자동 부여하지 않습니다.

삭제 허용/거부와 local 권한 연결에 직접 관련된 테스트 3개를 Java 21의 격리된 메모리 DB에서 실행해 통과했습니다. 실제 사용자 DB 삭제·서버 재시작은 하지 않았습니다. HTTP 계약은 [API](../api/api.md#데이터셋-삭제), 구현 진행은 [데이터셋 계획](../plans/dataset-development-plan.md)에서 관리합니다.
