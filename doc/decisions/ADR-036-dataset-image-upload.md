# ADR-036: 데이터셋 이미지 업로드와 원본 파일명 중복

- 상태: 채택 — 백엔드 구현·선별 검증 완료, 프런트 구현은 사용자 요청으로 취소, 실제 DB·서버 미적용
- 날짜: 2026-11-12
- 관련 기록: [ADR-035](ADR-035-dataset-deletion-authorization.md), [이미지 업로드 단계](../plans/backend/stage-04-ingestion-upload.md)

## 맥락

사용자는 데이터셋 상세에서 이미지 업로드와 원본 이미지명 저장을 요청했습니다. 원본명이 이미 같은 데이터셋에 있으면 실패 목록에 “이미 존재하는 이미지”로 표시해야 합니다. 사용자는 실제 파일은 로컬 저장, DB는 메타데이터 저장을 선택했고 업로드는 공간 운영자 또는 데이터셋 생성자에게 허용하도록 확인했습니다.

## 대안

- 바이너리까지 DB 저장: 사용자가 선택하지 않았습니다.
- 로컬 파일과 DB 메타데이터 분리: 현재 실행 환경에서 별도 저장소 의존성 없이 원본 파일을 보존할 수 있습니다.
- 원본명을 실제 저장 경로로 사용: 경로·동명 충돌 문제를 피하기 위해 사용하지 않습니다.

## 결정

원본 파일명은 DB에 보존하고 실제 파일은 서버 UUID와 검증한 이미지 형식의 확장자로 저장합니다. 저장 경로는 Spring YAML에서 지정합니다. 콘텐츠를 직접 판독하여 PNG·JPEG·GIF·BMP를 허용하고 파일당 10MB, 판독하는 첫 이미지 4천만 화소 이하로 제한합니다. 원본 바이트는 재인코딩하지 않습니다.

`UNIQUE(dataset_id, original_filename)`으로 같은 데이터셋 안의 중복만 금지합니다. 원본명은 클라이언트 경로를 제외한 basename이며 대소문자를 구분하고 나머지 글자를 임의 변경하지 않습니다. 같은 이름은 다른 데이터셋에 등록할 수 있습니다. 사전 확인과 DB 고유 제약을 함께 사용하여 동시 요청도 중복 저장하지 않습니다. 중복은 409입니다.

서비스 `@PreAuthorize`에 `dataset:image:upload`와 `datasetService.canManage(datasetId)`를 명시합니다. 활성 계정·활성 공간·ACTIVE 멤버십은 필수이고 OWNER·공간 ADMIN·데이터셋 생성자 중 하나여야 합니다. 실제 INSERT에도 같은 범위 조건을 적용합니다. 업로드 권한은 삭제 기능 권한과 독립적입니다. local admin에만 초기 권한을 명시적으로 부여하며 일반·운영 역할은 별도 할당해야 합니다.

사용자는 이후 프런트 화면 구현을 취소했습니다. 업로드 UI·클라이언트·관련 스타일 추가를 제거하고 백엔드만 유지합니다. API는 파일당 단건 업로드·원본명 포함 등록 목록·중복 409를 제공하며 향후 화면이 성공/실패 목록을 구성할 수 있습니다. 현재 상세 모달에 이미지 업로드 화면을 제공하지 않습니다. 상세 페이지 전환·미리보기·다운로드·배치는 추가하지 않습니다.

## 결과

파일 저장 후 DB 작업이 실패하면 트랜잭션 완료 콜백이 파일을 정리합니다. 실패 정리 자체가 실패하면 로그에 남기며 별도 재시도 배치는 없습니다. DB와 파일 저장소가 분산 트랜잭션으로 묶였다고 간주하지 않습니다.

dataset_image는 데이터셋 삭제 시 메타데이터가 함께 지워지도록 FK CASCADE를 사용합니다. 실제 이미지 파일 삭제는 이전 논의대로 후속이며 이번에 추가하지 않습니다. 파일은 UUID 경로이므로 나중에 DB 참조와 비교하여 정리할 수 있습니다. 과거 ADR-035의 이미지 메타데이터 미구현 상태는 이번 도입으로 변경됩니다.

계약은 [API](../api/api.md#데이터셋-이미지-업로드), [DB](../db-schema/tables/dataset/dataset-image.md), 설정·실행 제약은 [배포 문서](../operations/deployment.md#이미지-업로드-저장소--2026-11-12)를 기준으로 관리합니다. 실제 DB 적용과 사용자 서버 재시작은 하지 않았습니다.
