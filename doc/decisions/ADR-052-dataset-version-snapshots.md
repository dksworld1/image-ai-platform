# ADR-052: 데이터셋 버전의 전체 목록 스냅샷

- 상태: 채택 — 2026-11-23 버전 관리 백엔드·화면 구현
- 날짜: 2026-11-23
- 관련 기록: [데이터셋 버전 관리 설계 합의](../plans/dataset-development-plan.md#데이터셋-버전-관리-설계-합의--2026-11-23), [실행 파이프라인 설계](../plans/execution-pipeline-data-modeling.md#11-기존-데이터셋과-보존-정책)

## 맥락

사용자는 스테이지 입력으로 데이터셋 또는 아티팩트 여러 개를 전달하는 방안을 논의하면서 데이터셋 입력을 특정 시점으로 고정할 필요를 확인했습니다. 중간 버전 삭제에 따른 계보 단절, 삭제된 목록의 복원 필요성, 약 200개 목록에서 한두 파일만 바뀌어도 전체 구성을 저장하는 비용을 비교한 뒤 전체 스냅샷 방식에 동의하고 문서 반영을 지시했습니다.

## 대안

- 전체 목록 스냅샷: 메타데이터가 중복되지만 각 버전을 독립적으로 조회·재현할 수 있습니다.
- 변경분 저장: 기록량이 적지만 이전 상태와 삭제 기록을 순서대로 적용해야 합니다.
- 주기적 스냅샷과 변경분 혼합: 저장량을 줄이지만 복원·검증 경로가 복잡해집니다.

## 결정

현재 편집 가능한 데이터셋과 확정 버전을 분리하고 버전마다 전체 파일 구성 메타데이터를 저장합니다. 실파일은 고정된 개별 파일 버전을 참조하여 중복 복사하지 않습니다. 파일 교체·제외·설명 수정은 과거 스냅샷을 변경하지 않습니다.

확정 버전의 기록·구성은 수정·삭제하지 않고, 참조된 파일 행과 실제 파일도 물리 삭제하지 않는 초기 정책을 채택합니다. v3 복원에 v2의 삭제 이벤트가 필요한 구조로 만들지 않습니다. 실행 입력의 '최신' 선택은 실행 접수 시 구체적인 version_id로 고정합니다.

약 200개 항목에서 1,000개 버전은 약 20만 메타데이터 행이라는 규모 예시를 근거로 초기에는 복원·조회·보전의 단순성을 우선합니다. 실제 저장량·성능은 측정하지 않았으며 규모가 커지면 측정 후 변경분 방식 등을 재검토합니다.

## 결과

생성 알고리즘·스키마 후보·삭제 보호·후속 검증 기준의 상세는 관련 작업계획서를 따릅니다. 데이터셋 삭제의 기존 연쇄 삭제와 현재 활성 파일만 읽는 경로를 그대로 사용해서는 과거 버전을 보전할 수 없으므로 구현 시 함께 조정해야 합니다.

최초 승인은 설계·문서 반영에 한정됐으며, 2026-11-23 후속 지시로 [버전 관리 API](../api/api.md#데이터셋-전체-목록-버전--2026-11-23)·화면·[V27 테이블](../db-schema/tables/dataset/dataset-version.md)과 참조 삭제 보호를 구현했습니다. 과거 버전으로 현재 편집본을 준비하는 흐름은 후속 [ADR-053](ADR-053-edit-from-dataset-version.md)에서 구현했습니다. 요청 재시도 키·버전 보관 UI·자동 버전 생성·실행 포트의 구체적인 입력 바인딩은 후속 설계입니다.
