# ADR-040: 데이터셋과 이미지 기능 권한 분리

- 상태: 채택
- 날짜: 2026-11-13
- 대체/관련 기록: ADR-026·035·036·038·039. 이미지 읽기·수정의 기능 권한 방침을 대체하며 버전·파일 보존 방침은 유지
- 후속 구현: [ADR-041](ADR-041-image-logical-deletion.md)에 따라 개별 이미지 삭제 API·선택 삭제 화면을 구현했습니다. 아래 미구현 설명은 이 결정 당시 상태입니다.

## 맥락

이미지 보기와 수정 업로드가 각각 데이터셋 읽기·이미지 업로드 권한을 재사용하고 있었습니다. 사용자는 이미지를 별도로 관리하고 향후 워크스페이스 일반 사용자의 수정·삭제 대상 조건도 추가할 수 있도록 요청했습니다.

## 대안

- 데이터셋 기능 권한 재사용: 단순하지만 데이터셋 정보 조회와 이미지 조회·편집을 독립적으로 부여할 수 없습니다.
- 이미지 동작별 기능 권한과 대상 조건 분리: 명시적인 역할 부여가 필요하지만 기능 허용과 공간·대상 범위를 각각 관리할 수 있습니다.

## 결정

이미지는 dataset:image:read·upload·update·delete로 구분합니다. 목록·원본·썸네일은 read, 신규 업로드는 upload, 수정 업로드는 update를 서비스 @PreAuthorize에 명시하고 대상 조건을 AND로 검사합니다. 읽기는 활성 공간의 ACTIVE 멤버, 쓰기는 여기에 공간 OWNER·ADMIN 또는 데이터셋 생성자 조건을 추가합니다. 수정 업로드에서 같은 이름이 없어 신규 등록되는 파일은 upload 권한도 필요하며 데이터셋 행 잠금 뒤 실제 등록 분기에서 추가 검사합니다.

이미지 서비스는 데이터셋 상세 서비스를 호출하지 않습니다. 이미지 관리용 데이터셋 선택 목록도 이미지 read 권한의 별도 API로 제공하여 dataset:item:read 의존성을 제거합니다. 데이터셋 목록·상세 권한 자체는 변경하지 않습니다. 이미지 대상 SQL 조건은 데이터셋 삭제 SQL 조건과 분리하고, 사전 판정과 실제 이미지 변경에 같은 현재 대상 조건을 적용합니다.

개별 이미지 삭제 권한은 카탈로그에 등록하되 API·화면은 아직 구현하지 않습니다. 데이터셋 삭제에 따른 하위 이미지 처리와 삭제 이력 저장은 dataset:item:delete로 승인된 작업이며 이미지 기능 권한을 추가로 요구하지 않습니다.

## 결과

common seed는 카탈로그만 등록하고 local seed는 기존 admin 역할에 네 이미지 권한을 명시적으로 부여합니다. 다른 역할에 새 권한을 자동 전파하지 않습니다. 기존 역할은 필요한 새 권한을 별도로 부여해야 합니다.

canUpload·canUpdate와 SQL 대상 판정을 별도로 관리하므로 향후 일반 사용자에게 본인 등록 이미지·상태·기간 등의 조건을 추가할 수 있습니다. 추가 시 사전 판정과 실제 변경 SQL을 함께 갱신해야 하며, 이번 결정만으로 해당 정책이나 정책 테이블을 구현하지 않습니다. 권한명은 동작을 나타내고 세부 범위 조건을 권한명에 섞지 않습니다.

현재 계약은 [API](../api/api.md#이미지-기능-권한), 운영 적용은 [마이그레이션](../operations/database-migration.md), 검증은 [수집 단계](../plans/backend/stage-04-ingestion-upload.md#이번-구현-검증)를 따릅니다.
