# ADR-014: 클래스 초기화 기반 런타임 설정과 정적 접근

- 상태: 채택
- 날짜: 2026-11-07
- 대체/관련 기록: ADR-013 (Spring 초기화 전 설정의 별도 관리 원칙 추가)

## 맥락

Spring 초기화 전에 필요한 설정을 별도 파일에서 읽고 모든 클래스에서 정적 접근으로 사용할 수 있어야 합니다. 문자열 키는 중앙 로더에서만 다루고 소비자는 명시적 필드 접근자를 사용합니다. 초기화는 `main()` 호출 순서가 아니라 JVM의 클래스 초기화로 수행합니다.

## 대안

- `main()`에서 명시적으로 초기화: 호출 순서에 의존하며 사용자 요구와 맞지 않습니다.
- Spring 빈에서 초기화: Spring 초기화 전 사용하는 정적 코드에 제공할 수 없습니다.
- 정적 필드 초기화와 불변 객체: 최초 사용 시 JVM이 초기화를 수행하며 별도 초기화 호출 없이 정적 접근을 제공합니다. 이를 채택합니다.

## 결정

### 파일과 설정 경계

- Spring 초기화 전 필요한 설정은 주제별 UTF-8 `.properties` 파일로 관리합니다. Java 표준 `Properties.load(Reader)`와 UTF-8 Reader를 사용해 별도 YAML 파서 의존성을 추가하지 않습니다.
- 일반 애플리케이션 설정은 ADR-013의 주제별 Spring YAML로 유지합니다. Spring의 초기 설정 로딩으로 처리할 수 있는 값까지 런타임 설정으로 옮기지 않습니다.
- JVM 시작 전에 필요한 옵션은 실행 스크립트의 책임입니다. 이미 시작한 JVM 내부에서 이 모듈로 적용하지 않습니다.
- 클래스패스의 `config/runtime/` 바로 아래에 있는 모든 `*.properties`를 자동 탐색해 로딩합니다. 하위 디렉터리는 탐색하지 않습니다. IDE 실행과 패키징된 JAR 실행을 모두 지원합니다.
- 발견한 파일은 리소스 경로 순서로 읽고 중복 키는 오류 처리합니다. 동일 경로의 리소스가 여러 클래스패스 위치에서 발견되어도 임의로 하나를 선택하거나 덮어쓰지 않고 오류 처리합니다.
- 새 설정은 `RuntimeSettings` 또는 해당 주제의 불변 하위 객체에 명시적 필드를 추가하고 중앙 로더의 매핑을 함께 추가하는 방식으로 관리합니다. 파일 자동 탐색은 설정 필드의 자동 생성이나 동적 키 접근을 의미하지 않습니다.
- 실제 설정 항목과 주제별 파일명은 구현 전에 확정합니다. 환경 변수는 불가피한 경우에만 사용하며 비밀값이 포함된 파일은 저장소 밖에서 관리합니다. 클래스패스 파일에 실제 비밀값을 넣어 패키징하지 않습니다. 외부 비밀 설정 파일 로딩 방식은 별도 확정이 필요합니다.

### 클래스와 패턴

공통 기반인 `com.imageaiplatform.foundation` 아래에 구성합니다. 세부 패키지는 기존 코드 구조에 맞춰 구현 시 정합니다. 정적 Facade를 통해 하나의 불변 설정 객체를 제공하는 구조입니다.

| 클래스 | 책임 |
|---|---|
| `RuntimeSettingsLoader` | 중앙 로더. 주제별 파일 읽기, 문자열 키와 필드 매핑, 타입 변환 및 필수값 검증 |
| `RuntimeSettings` | 명시적 타입과 필드를 갖는 불변 설정 객체. 실제 주제별 분리가 필요할 때 불변 하위 객체로 구성 |
| `RuntimeConfig` | `private static final` 필드 초기화로 로더를 호출하고 `settings()` 정적 메서드로 설정 제공 |

설계 골격은 다음과 같습니다. `load()`는 클래스패스 `config/runtime/`의 파일을 탐색하며 실제 설정 필드는 아직 미정입니다.

```java
public final class RuntimeConfig {

    private static final RuntimeSettings SETTINGS =
            RuntimeSettingsLoader.load();

    private RuntimeConfig() {
    }

    public static RuntimeSettings settings() {
        return SETTINGS;
    }
}
```

소비자는 `RuntimeConfig.settings()`에서 반환된 객체의 명시적 필드 접근자를 사용합니다. 문자열 키 조회, 변경 가능한 `Properties` 객체 및 범용 서비스 등록 기능은 외부에 제공하지 않습니다. 필수값은 로딩 시 검증하고 DTO·record 필드는 저장소의 래퍼 타입 원칙을 따릅니다.

### 초기화와 접근 순서

1. 일반 메서드, 정적 메서드, 정적 필드 초기화 또는 정적 블록에서 `RuntimeConfig.settings()`를 최초 호출합니다.
2. JVM이 `RuntimeConfig`의 클래스 초기화를 수행하고 중앙 로더가 파일을 읽습니다.
3. 모든 값의 변환·검증이 성공하면 완성된 불변 객체를 `SETTINGS`에 저장합니다.
4. 클래스 초기화 완료 후 접근 메서드가 설정 객체를 반환합니다. 이후 호출은 같은 객체를 사용합니다.

`main()`에서 초기화하거나 로딩을 유도하는 호출을 추가하지 않습니다. 정적 초기화는 프로세스 시작 즉시 실행된다는 의미가 아니라 해당 클래스의 최초 사용 시 실행됩니다. Spring 시작 전에 설정을 소비하는 코드가 있으면 그 접근 시점에 로딩됩니다.

JVM의 클래스 초기화 규칙을 사용하므로 별도 `initialize()`, `volatile`, 동기화 초기화 메서드는 필요하지 않습니다. 엄밀한 초기화 단위는 `RuntimeConfig`를 정의한 클래스 로더별입니다.

### 의존성과 오류 처리

- 로더와 설정 객체는 Spring 빈·`Environment`에 의존하지 않습니다.
- 로더와 설정 객체가 `RuntimeConfig` 또는 이를 사용하는 클래스를 역참조하지 않도록 해 순환 초기화를 피합니다.
- 필수 파일·필수값 누락과 형식 오류는 초기화 실패로 처리하며 부분 설정을 제공하지 않습니다. 오류에는 파일과 키를 표시하고 비밀값은 출력하지 않습니다.
- 클래스 초기화 중 예외가 발생하면 최초 접근은 `ExceptionInInitializerError` 등으로 실패할 수 있으며, 이후 접근도 해당 클래스의 초기화 실패로 사용할 수 없습니다. 동일 클래스 로더에서 재시도하거나 설정을 교체하는 기능은 제공하지 않습니다.
- 실행 중 수정·재로딩·초기화 해제는 제공하지 않으며 변경 적용은 재시작을 기준으로 합니다.

## 결과

모든 클래스가 명시적 필드 접근자를 통해 동일한 런타임 설정에 정적으로 접근할 수 있습니다. 전역 접근과 불변 수명 때문에 같은 클래스 로더 안에서 서로 다른 설정을 동시에 사용하거나 테스트마다 설정을 교체하는 데 제약이 있습니다.

중앙 로더는 독립 테스트하고 정적 접근·동시 최초 접근·초기화 실패는 별도 JVM 또는 격리된 클래스 로더에서 검증합니다. 구현 상태와 실제 검증 결과는 [설정 모듈 단계 문서](../stages/stage-application-settings.md#현재-구현)에서 관리합니다.

파일 탐색은 여러 properties 파일의 통합, 하위 디렉터리 제외, 중복 키·중복 리소스 오류 및 패키징된 JAR에서의 로딩을 검증합니다.

### 구현 기록 (2026-11-07)

리소스 탐색에는 기존 Spring Core 유틸리티를 사용하고 properties 로딩은 Java 표준 API를 사용합니다. Spring 컨테이너·빈·Environment와 무관하게 클래스 초기화 시 실행됩니다. 현재 실제 설정 항목이 없으므로 필드와 필수값 검증은 항목 추가 시 구현합니다. 현재 필수 파일은 없으며 리소스가 없어도 빈 설정을 허용합니다.
